第１章 / コンパイラの出力を知る

機械語と
アセンブラ

ソースコードの向こう側で、何が起きているのか。
命令・値・実行位置の３つを手がかりに、CPUの動きを読み解く。

この章の到達点

「コンパイラが何を出力するか」と「関数からどう戻るか」を、自分の言葉で説明できる。

対象：x86-64・Linux・Intel記法。原書の章を入口にした、自作の図解と確認問題を含む補助教材です。原書を読む ↗

01CPUの見ている世界

プログラムの実行を追うときは、どの命令を読むかとどこに値があるかを分けて見る。命令もデータもメモリにあり、CPUは命令を読み、レジスタやメモリの状態を変えていく。

レジスタはCPU内部の小さな記憶領域。RIPは命令の位置を扱うレジスタで、プログラムカウンタに相当する。通常は次の命令へ進み、分岐では別の場所へ進む。

アドレスは「場所」、その場所にあるデータは「中身」。この２つを混ぜないことが、後のポインタやスタックの理解につながる。ここではキャッシュや仮想メモリを省いた概念図として見る。

ビット・バイト・命令の関係

メモリの中身を８ビットずつ区切ると、１区切りが１バイトになる。下の２行は同じデータを、２進数と16進数で表したもの。16進数なら、１バイトを２桁で書ける。

１バイト＝１命令ではない。 x86-64の命令は長さが一定ではない。この例の 48 89 F8 は、３バイト（24ビット）で１命令になる。

CPUはどこで命令を区切る？

CPUは「ここで終わり」という記号を探すのではなく、命令の形式に必要な情報がそろったかで判断する。今の例を、先頭から追ってみよう。

「幅の指定 → 操作 → 対象」がそろい、この形式に必要な情報を読み終えたので、３バイトで区切れる。別の形式なら、さらにアドレスを計算する情報や定数を読むこともある。

実際のCPUが１バイトずつ時間をかけて読む様子ではなく、デコードの判断を順に示した概念図。参照：Intelの命令形式の解説。

補足：RIPが保持するアドレスは１つだけ

この図で命令の位置を示すRIPが保持するのは、命令の最初のバイトのアドレス A だけ。３バイトの命令でも、A・A + 1・A + 2 の３つをまとめて保持するわけではない。

CPU内部の読み出し回路は、先頭の A を基準に続きのバイトを取得する。２番目の場所は A + 1、３番目は A + 2 と求められるので、それぞれのアドレスをRIPに保存しておく必要はない。

この命令が３バイトだとわかれば、順に進む場合の次の命令の位置は A + 3 になる。RIPはアドレスの一覧ではなく、１つの命令位置を示す。

補足：３バイトの命令で、64ビットの値を扱える？

命令自体の長さと、命令が扱う値の幅は別のもの。

今回の大きさ何の大きさ？
３バイト＝24ビット48 89 F8 という命令そのものを記録する大きさ。
64ビット＝８バイトその命令がRDIからRAXへコピーする値の幅。

この 48 は「コピーする対象を64ビット幅として扱う」という指定。命令自身を64ビットにする指定ではない。

命令にはコピーする値そのものを埋め込まず、「RDIからRAXへコピーする」という操作と対象を記録している。値はレジスタにあるので、３バイトの短い命令でも64ビットの値を操作できる。

02言葉から機械語へ

アセンブリは命令を文字で記述する言語、アセンブラはその記述を変換するプログラム。CPUが実行するのは、変換された機械語のバイト列だ。

アセンブルしただけでは、別のファイルにある関数の位置が未確定なことがある。リンカは部品を結びつけ、参照先などを解決する。図では前処理を省略している。GCCの処理段階 ↗

機械語の読み方は命令セット（ISA）が定める。ここで扱うx86-64のバイト列を、別のISAのCPUがそのまま同じ命令として実行できるわけではない。

オブジェクトと実行ファイルの中身

オブジェクトファイルは、ソースファイル１つ分の部品。機械語は入っているが、別の部品にある関数の住所がまだ決まっていないことがある。実行ファイルは、リンカが部品を結合して、参照先や起動地点を整えた実行用のまとまりだ。

main.oだけでは、addの実体が別ファイルにあるため実行ファイルにできない。リンカはシンボルと再配置情報を使って参照先を埋める。動的リンクを使う場合は、実行時に共有ライブラリを組み合わせる部分も残る。

03アセンブリを読む

まずは、値を返す処理を２つに分ける。返り値を置く処理と、呼び出し元に戻る処理だ。

C：13を返す関数
int value(void) {
    return 13;
}
対応する命令の一例
value:
    mov eax, 13
    ret

手書きの命令部分です。コンパイラの実際の出力は最適化などで変わります。EAXはRAXの下位32ビットを指し、この環境のCの int の返り値に使います。EAXへの書き込みでRAXの上位32ビットはゼロになります。

読むポイント意味
mov eax, 1313をEAXに入れる。Intel記法の mov は左が書き込み先。
ret保存されている戻り先へ移る。返り値を計算する命令ではない。
value:位置につけた名前（ラベル）。CPUの実行命令ではない。
.intel_syntax noprefixIntel記法を指定するアセンブラへの指示。これもCPUの命令ではない。

記法の確認：GNUアセンブラの仕様 ↗

逆アセンブルの表示は、３つに分けて読む

表示の読み方を示すための例。位置は仮の値で、実行時の絶対アドレスとは限りません。逆アセンブルは機械語を命令表記に戻す操作で、元のCの変数名や構造を完全に復元するものではありません。

04呼び出して、戻る

呼び出す側：戻ってから１を足す
    call value    # ① valueへ移る
after_call:
    add eax, 1    # ④ ここから再開。13 → 14
    # 呼び出し元の処理が続く
呼び出される側：13を返す
value:
    mov eax, 13   # ② 返り値を用意する
    ret           # ③ after_callへ戻る

別々の場所にある命令の抜粋（Intel記法）。呼び出し前後のスタック調整などは省略しています。after_call: は、call の直後にある add 命令の位置につけた名前です。

call value が保存するのは、after_call のアドレス。ret はそのアドレスをスタックから取り出すので、call を繰り返さず、次の add から再開できる。返り値の13はEAX、戻り先のアドレスはスタックにあり、役割が違う。

ret に戻り先のアドレスが書かれているわけではない。概念的には RIP = メモリ[RSP]、その後に RSP を８増やす命令。関数がローカル変数などでスタックを使った場合は、ret の前にRSPを戻り先アドレスの位置へ戻しておく。

関数呼び出しでは、値の受け渡しに加えて、処理の続きをどこから再開するかを覚える必要がある。x86-64の call は次の命令のアドレスをスタックに積み、呼び出し先へ移る。ret はそれを取り出して戻る。

スタックはメモリ上の領域で、最後に積んだものから取り出す。RSPはその先頭を指すレジスタだ。戻り先を積んでおけば、呼び出しが入れ子になっても、内側の関数から順に戻れる。

メモリ全体では、どこに何がある？

１つの実行中のプログラム（プロセス）から見える仮想アドレス空間には、命令を置く場所、長く残すデータ、実行中に確保するデータなどがある。スタックはその一部。この図も、これまでのスタック図と同じく上が低いアドレス、下が高いアドレスだ。

スタックの「余地」は、確保済み、またはOSなどの管理のもとで拡張できる範囲をまとめて描いている。低い側の空間を無制限に使えるわけではなく、範囲外へのアクセスを検出するための保護領域が設けられることもある。また、ローカル変数がすべてスタックに置かれるわけではなく、レジスタに置かれたり、最適化で消えたりする。

Linuxでは /proc/<PID>/maps で、実際に対応付けられた領域とアクセス権を確認できる。参照：Linuxのメモリ配置の資料。malloc による確保は、連続したヒープのほか、別のマッピングを使うこともある：動的メモリ確保の資料。

命令・返り値・戻り先は、それぞれどこにある？

value: の下の命令は、メモリのコード領域に置かれる。mov eax, 13 はCPU内のEAXに13を書き込む命令。この例でスタックに積むのは、call が保存する戻り先のアドレスだ。

メモリ上では、スタックはどう並ぶ？

スタックも、アドレスの付いたメモリの一部。使う範囲を広げるときは、x86-64では低いアドレス側へ先頭を動かす。下の図は、戻り先を１つ積み、取り出すまでの変化だ。

スタック全体のうち５マスだけを抜き出した概念図。最初から５マスだけ確保されているという意味ではない。通常、OSなどが用意したスタック領域の中でRSPを動かして使う。図のアドレスはプログラムから見えるもので、物理メモリの配置を示すものではない。

命令を１つずつ進めてみる

独自の観察用モデル：long の２つの値、5と8を足して返す場面。命令の前に引数を用意し、最後は呼び出し元の「続き」で止まります。

関数呼び出しの観察緑の行＝次に実行する命令
呼び出し元
01mov rdi, 5
02mov rsi, 8
03call sum
04… 続き
sum:
05mov rax, rdi
06add rax, rsi
07ret
レジスタの値 / — はまだ未設定
RDI / 第１引数—
RSI / 第２引数—
RAX / 返り値—
RSP：0x1000戻り先はまだ積んでいない

ここでのスタック表示は、この呼び出しが使う部分のみ。アドレスは説明用の仮の値です。

0 / 6

値を渡す約束と、CPUの命令を分ける。 RDI・RSIで整数引数を渡し、RAXでこの整数結果を返すのは、本書の環境の呼び出し規約。call 自体が引数を選んで渡すわけではない。実装時にはスタックの整列などの約束も守る。この図は整列済みの呼び出し直前から始めている。

05理解を確かめる

答えを開く前に、頭の中で短く説明してみる。

問１mov rax, rdi のあと、RDIの値は消える？

消えない。値のコピーなので、RDIは5のまま、RAXも5になる。命令名を「移動」と訳すだけでは、状態変化を読み違えやすい。

問２call を単なるジャンプにすると、何が足りない？

戻り先の保存が足りない。飛ぶことはできても、対応する ret が取り出す戻り先を、そのジャンプはスタックに積んでくれない。

問３関数の返り値13は、スタックから取り出す？

この例ではRAXにある。スタックから取り出すのは「戻り先のアドレス」。結果の値と実行を再開する場所は、別々に受け渡す。

問４Cからアセンブリを出せたら、すぐCPUで実行できる？

アセンブリは文字なので、アセンブルが必要。さらに必要な部品をリンクして実行ファイルにし、読み込んで実行する。本書のコンパイラは、その手前のアセンブリ出力を担当する。
