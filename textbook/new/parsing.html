第４章

構文解析

数と記号の並びから、「何と何を、どう組み合わせるか」を取り出す。

前章では、2+3*4 を数２、＋、数３、＊、数４に分けました。今回は、この並びから「３と４を掛け、その結果を２に足す」という構造を作ります。その構造を目で見える形に出力し、括弧を加えるとどこが変わるかを確かめます。

１この章で扱う問い

演算子の優先順位や括弧を、どう構造として表すか？

2+3*4 と (2+3)*4 は、数も演算子も同じですが、組み合わせ方が違います。また、9-3-2 では、左から引くのか、右側を先にまとめるのかでも結果が変わります。こうした違いを、後の処理が迷わず使える構造にします。

前提は第３章のトークンと読み取り位置です。今回もＣで実装しますが、関数の役割、渡す情報、返す構造を順に説明します。本章の出力は木構造で、計算結果やアセンブリではありません。木から命令を作る工程は第５章で扱います。

２この章の理論

トークンの「並び」に、親子関係を与える

構文解析は、トークンの並びが言語の規則に合うか確かめ、その組み立てを取り出す処理です。今回の出力は抽象構文木と呼ぶ木構造で、略して AST とも書きます。

木を構成する一つ一つの要素をノードと呼びます。数のノードは値を持ち、演算子のノードは左と右に計算対象のノードを持ちます。その対象がさらに演算なら、そこにも子があるため、式全体を階層として表せます。木の一番上を根、子を持たない数のノードを葉と呼びます。

優先順位を、読む範囲の違いで表す

文字列を見てから思いつきで順序を選ぶのではなく、受け付ける並びを文法として先に決めます。今回の文法は次の３段階です。

expr    = mul (('+' | '-') mul)*
mul     = primary (('*' | '/') primary)*
primary = 数 | '(' expr ')'

= は左のものの組み立て方、| は「どちらか」、末尾の * は「直前のまとまりを０回以上繰り返す」を意味します。引用符内の '*' は入力中の掛け算記号で、繰り返しを表す末尾の * とは役割が違います。引用符は記号を示すための表記で、入力に書く必要はありません。

  • primary は、数一つ、または括弧で囲まれた式一つを読む。
  • mul は、まず一つの primary を読み、＊や／が続けば次の primary とまとめる。
  • expr は、まず一つの mul を読み、＋や－が続けば次の mul とまとめる。

名前は、expr が式全体、mul が乗除算のまとまり、primary が基本のまとまり、という役割を表します。数一つだけでも、繰り返しを０回にできるので mul や expr として読めます。

この段階分けにすると、足し算の右側を作るとき、mul が 3*4 を先に一つの木にまとめて返します。掛け算を優先する規則は、足し算が乗除算のまとまりを受け取る構造に埋め込まれています。

文法の各段階を、関数にする

この文法に対応して、expr、mul、primary というＣの関数を作ります。それぞれ必要なトークンを読み、その範囲に対応する木の根を返します。規則に沿って関数を呼び下りるため、この方法を再帰下降構文解析と呼びます。

ここでの読み取り位置 cursor は、文字の位置ではなくトークン配列の添字です。第３章の pos と区別します。関数から戻ったときには、読んだ範囲の次のトークンを指しています。

同じ優先順位なら、左側を積み重ねる

9-3-2 は (9-3)-2 と解釈します。このように同じ優先順位の演算が左からまとまる性質を左結合と呼びます。＋と－、＊と／を、それぞれ同じ優先順位で左結合にします。

括弧の中では、式全体をもう一度読む

primary が開き括弧を見つけたら、内側を読むために expr を呼びます。expr は乗除算や加減算をまとめ、閉じ括弧の手前で返ります。呼んだ側の primary が閉じ括弧を確認して消費し、中で作った木を返します。

(2+3)*4 なら、内側の expr が「２＋３」の木を返し、外側の mul はそれを一つの左側として扱います。そのため、外側の＊は「２＋３」の木と４を子に持ちます。

括弧が入れ子なら、同じ仕組みでもう一度 expr を呼びます。expr → mul → primary → expr と関数の呼び出しが循環するのが、ここでの再帰です。再び呼ぶ前には開き括弧を消費するので、同じ場所で際限なく呼び続ける構造ではありません。

実装の状態と、木を表すデータ

完成した実装は parse.c に用意しました。前章のファイルを変更せず、同じ字句解析規則をこのファイルにも入れています。トークンの長さは今回使わないため省略し、種類・開始位置・数値を保持します。

typedef struct Node Node;
struct Node {
    char op;
    int value;
    Node *left;
    Node *right;
};

Node は木の一要素です。op が '\0' なら数の葉で、value を使います。op が '+' などなら演算ノードで、left と right を使います。Node * は別のノードの場所を指すポインタです。子のノードそのものを丸ごと複製するのではなく、その場所を覚えてつなぎます。

Parser 構造体は、入力文字列、トークン配列、現在の cursor、ノードを保存する配列などをまとめたものです。各関数に Parser *p を渡し、同じ読み取り位置と保存領域を共有します。p->cursor は、p が指す構造体の cursor を使う書き方です。

一致した記号だけを読む consume

static bool consume(Parser *p, char symbol) {
    Token token = p->tokens[p->cursor];
    if (token.kind != SYMBOL || p->source[token.start] != symbol) {
        return false;
    }
    p->cursor++;
    return true;
}

consume(p, '+') は現在のトークンが＋なら一つ進んで true、違えば位置を変えずに false を返します。記号でなければ、|| の右側を評価せずに判定が終わります。static は、この関数をこのＣファイル内で使う指定です。

一致しないときに進まないことが重要です。mul が＋を見ても、その＋を残して戻れば、呼び出し元の expr が読むことができます。

expr は、乗除算の木を加減算でまとめる

static Node *expr(Parser *p) {
    Node *node = mul(p);
    if (node == NULL) return NULL;
    for (;;) {
        char op;
        if (consume(p, '+')) op = '+';
        else if (consume(p, '-')) op = '-';
        else return node;
        Node *right = mul(p);
        if (right == NULL) return NULL;
        node = new_node(p, op, 0, node, right);
    }
}

最初の mul(p) で左側の木を受け取ります。for (;;) は繰り返しで、＋でも－でもなくなったら return node で終わります。演算子を読めたら、右側も mul に作らせます。

new_node は新しいノードの保存場所を取り、演算子・値・左の子・右の子を設定して、その場所を返す補助関数です。ここでの０は使わない数値欄です。node = new_node(..., node, right) が、それまでの木を左の子にし、新しい根を node にする操作です。これが図３の左結合を実現します。

NULL は木を返せないことを表す値として使っています。下の関数が失敗したら、そのまま上へ失敗を返し、不完全な木を完成した出力として表示しません。mul も同じ形で、呼ぶ相手を primary、記号を＊と／に変えています。

primary が数と括弧を受け持つ

static Node *primary(Parser *p) {
    if (consume(p, '(')) {
        Node *node = expr(p);
        if (node == NULL) return NULL;
        if (!consume(p, ')')) return fail(p, "閉じ括弧が必要です。");
        return node;
    }
    Token token = p->tokens[p->cursor];
    if (token.kind != NUMBER) return fail(p, "数または開き括弧が必要です。");
    p->cursor++;
    return new_node(p, '\0', token.value, NULL, NULL);
}

開き括弧なら内部の式へ、そうでなければ数へ進みます。! は判定の否定なので、閉じ括弧を消費できなければエラーです。fail は現在のトークンの文字位置と理由を標準エラー出力に書き、NULL を返します。数を読む場合は子がないため、左右を NULL にした葉を作ります。

primary の定義時点で expr を呼べるように、ファイルには先に static Node *expr(Parser *p); という宣言を置いています。宣言は関数の入出力をＣコンパイラに知らせるもので、その場での実行ではありません。

式を作れた後も、入力の最後を確かめる

最上位では、expr が木を返した後、現在のトークンが END か確認します。これがないと、1 2 の最初の１だけを正しい式として受け取り、残りを無視してしまいます。括弧内では primary が閉じ括弧を確認し、式全体の外では main が入力の終了を確認する、という分担です。

本章の言語は、０〜２５５の数、二項演算の＋・－・＊・／、括弧です。-3 のような単項演算はまだ扱いません。安全に小さな実験をするため入力は１０２４バイトまでに制限し、ノードの保存領域はまとめて確保・解放します。除算の実行やゼロ除算の扱いも、この段階では行いません。

３ハンズオン

準備：木を表示するプログラムを作る

第３章と同じコンテナ内で実行します。入り直す場合は、マック側のリポジトリで make -f docker.mk shell を実行してください。

cd /workspace/textbook/new/labs/ch04
gcc -std=c11 -Wall -Wextra -o /tmp/ch04-parse parse.c

cd で第４章の実験フォルダへ移動し、gcc で構文解析器自身を実行ファイルにします。ビルドの成功を確認してから次へ進みます。今回の出力は (演算子 左の子 右の子) の表記です。たとえば (+ 2 3) は、根が＋、左右の子が２と３である木を表します。

子がさらに木なら、その場所にも括弧付きの表記を入れます。表示の括弧は木の形を明示するために付けるもので、元の入力の括弧をそのまま再表示しているわけではありません。print_tree が左右の子をたどって、この文字列を書き出します。

実験１：優先順位を木で確認する

根になる演算子と、その左右の子を先に予想してください。計算した数値より、木の形に注目します。

/tmp/ch04-parse '2+3*4'
echo $?

引用符は入力全体を一つの引数にし、＊をシェルがファイル名として展開するのも防ぎます。echo $? は構文解析器の終了状態を表示します。

実行後に開く：どちらが根になるか
(+ 2 (* 3 4))

根は＋、右の子が掛け算の木です。終了状態は０で、構文解析の成功を表します。１４を計算して返しているわけではありません。

実験２：括弧で構造を変える

/tmp/ch04-parse '(2+3)*4'
/tmp/ch04-parse '((2+3))*4'

実験１から根と子がどう入れ替わるかを予想します。さらに、括弧を二重にするとノードが増えるか考えてください。

比較後に開く

どちらも (* (+ 2 3) 4) になります。括弧内の式を primary が一まとまりで返すため、根は＊です。括弧そのもののノードは作らないので、同じまとまりを二重に囲っても木の形は変わりません。

実験３：引き算の結び付き方を見る

/tmp/ch04-parse '9-3-2'
/tmp/ch04-parse '9-(3-2)'

紙やメモに２つの木を描いてから実行します。２番目の－が、左の子に入るか、右の子に入るかを確認します。

比較後に開く

最初は (- (- 9 3) 2)、次は (- 9 (- 3 2)) です。最初はループが左側の木を積み重ね、次は括弧内の木が右側として返ります。もし計算するならそれぞれ４と８になりますが、このプログラムは木を表示するところで止まります。

実験４：エラーになった位置と理由を追う

/tmp/ch04-parse '9 +'
echo $?
/tmp/ch04-parse '(2+3'
echo $?
/tmp/ch04-parse '1 2'
echo $?

どれも前章の字句解析には成功する入力です。今度はどこで期待と合わなくなるか、入力の文字位置を０から数えて予想します。

実行後に開く
  • 9 +：位置３で、数または開き括弧が必要。右側を読もうとして終了トークンに出会います。
  • (2+3：位置４で、閉じ括弧が必要。内側の式を作った後の確認で失敗します。
  • 1 2：位置２で、余分なトークン。最初の式を作った後の終了確認で失敗します。

それぞれ終了状態は１です。エラー位置はトークンの個数ではなく、トークンが記録している入力内のバイト位置です。

実験５：終了確認を外したら何を見落とすか

マック側の別ターミナルでファイルを開きます。

nvim /Users/hatasatoki/Develops/compilerbook/textbook/new/labs/ch04/parse.c

main 内の次の３行を、一時的にコメントにするか外します。元の内容を戻せるようにしておきます。

if (root != NULL && tokens[parser.cursor].kind != END) {
    root = fail(&parser, "式の後に余分なトークンがあります。");
}

コンテナ側で再ビルドし、同じ入力を試します。

gcc -std=c11 -Wall -Wextra -o /tmp/ch04-parse parse.c
/tmp/ch04-parse '1 2'
echo $?
変更後に開く：部分的な成功に気付く

木として１だけが表示され、終了状態が０になります。expr は＋や－でない数２を見て、そこまでの木を返します。入力全体を読み切ったか確かめる役が消えたため、余りが見逃されます。

確認後は３行を元に戻して再ビルドし、1 2 が再び拒否されることを確認します。式を一つ読めることと、入力全体が正しいことの違いを説明できれば、この実験の区切りです。

４理解チェック

8/2/2 と 8/(2/2) の木は？

解説を読む

それぞれ (/ (/ 8 2) 2) と (/ 8 (/ 2 2)) です。＊・／も左結合なので、括弧がなければ最初の除算を左の子に積み重ねます。

2*(3+4) の括弧の中で、＋を読めるのはなぜ？

解説を読む

primary が開き括弧を読んだ後、内部の expr を呼ぶからです。外側では掛け算を読んでいても、括弧の中では加減算を含む式全体を読めます。閉じ括弧は呼び出し元の primary が確認します。

mul が＋を見たとき、なぜ位置を進めずに戻る？

解説を読む

＋は呼び出し元の expr が読む記号だからです。ここで飛ばすと、次の処理が式のつながりを判断するための情報を失います。

-3 と 3/0 は、このプログラムで受け付ける？

解説を読む

-3 は字句解析には成功しますが、今回の primary は先頭の－を扱わないため構文エラーです。3/0 は (/ 3 0) という木になります。構文として正しいことと、その計算を実行してよいことは別です。このプログラムは割り算を実行しません。

構文解析器が０で終了したら、式の値も０？

解説を読む

０は構文解析器が入力全体を正しく読めたことを示します。出力は標準出力に表示された木です。木の計算結果を終了状態で返しているわけではありません。
