第１２章

スタティックリンクと
ダイナミックリンク

関数の実体を取り込むか、外に置いたまま結び付けるか。

第６章では別々のオブジェクトファイルを結合し、第１１章では実行ファイルがメモリへ用意される過程を見ました。今回はその間にある「ライブラリとの結び付き」を調べます。

１この章で扱う問い

実行ファイルを作り直していないのに、呼び出す関数の結果が変わることはあるか？

７を返す answer という関数を、別ファイルへ置きます。同じ呼び出し側から二つの実行ファイルを作り、後で関数を４２を返すものへ差し替えます。どちらが変わるかを予想し、ファイル内の情報と実際の出力を照合します。

対象はリナックス x86-64、ＧＣＣとＥＬＦ形式です。自作コンパイラに構文を追加する章ではありません。自作コンパイラが出したコードも、外部関数を使うときには、このようなリンクの仕組みにつながります。

２この章の理論

宣言だけでは、関数の命令は存在しない

int answer(void);
int main(void) {
    printf("%d\n", answer());
    return 0;
}

これは呼び出し側の抜粋です。完全な main.c には stdio.h の読み込みもあります。int answer(void); は「引数なし、戻り値は int」と伝える宣言で、関数の本体ではありません。本体は answer.c にあり、最初は７を返します。

main.c を -c で変換すると main.o ができます。しかし、そこには answer の本体がありません。名前と、後で呼び出し先を結び付けるための情報が残ります。第６章の「未解決の参照」です。ここから実体を用意する方法を二つ比較します。

静的リンク：必要な部品を実行ファイルへ取り込む

スタティックリンク（静的リンク）では、リンク時に必要なオブジェクトのコードやデータを出力ファイルへ取り込み、参照を結び付けます。.a はオブジェクトファイルをまとめたアーカイブです。今回の libanswer.a には answer.o を一つだけ入れます。

通常、アーカイブの全メンバーを無条件に取り込むのではなく、未解決の名前を満たすメンバーを選びます。今回なら main.o が必要としている answer を定義する answer.o が選ばれます。出来上がった archive-app は answer の実体を持つため、実行時に libanswer.a を読み直す必要はありません。

ここで「静的」なのは answer との結び付きです。今回の archive-app は、標準Ｃライブラリについては通常どおり動的リンクします。「.a を一つ使った」ことと「プログラム全体を完全に静的リンクした」ことは違います。全体を対象とする -static は今回使いません。

動的リンク：実体を別ファイルに置いておく

ダイナミックリンク（動的リンク）では、共有ライブラリ .so の実体を、実行ファイルの外に残します。ビルド時のリンカーはライブラリを調べ、必要なライブラリの名前や、実行時に参照を解決するための情報を実行ファイルへ記録します。ビルド時のリンクがなくなるわけではありません。

起動時には、第１１章で出てきた動的リンカーが共有ライブラリを見つけ、メモリへ用意し、関数などの参照を結び付けます。関数の結び付けを初回呼び出しまで遅らせる方式もあります。いずれも、Ｃソースを起動のたびにコンパイルするのではなく、すでに機械語になった部品を接続します。

名前を探す場所も、二段階ある

ビルド時の -L は、リンカーがライブラリを探すディレクトリを増やす指定です。-lanswer は libanswer という名前のライブラリを選ぶ指定で、今回の環境では同じ場所に .so と .a があると通常は .so が選ばれます。静的側は曖昧さを避け、.a のパスを直接渡します。

-L を書いただけでは、起動時の検索先は設定されません。今回は -Wl,-rpath,'$ORIGIN' で実行ファイルのあるディレクトリを検索先として記録します。-Wl, は後続の指定をＧＣＣからリンカーへ渡す記法です。$ORIGIN は実行時の仕組みが解釈する印で、シェルに先に展開させないため単一引用符で囲みます。現在の作業ディレクトリ、という意味ではありません。

現代のＧＮＵの環境では、この検索先は通常 RUNPATH として見えます。環境変数やシステムの検索先も関係しますが、実験では同じディレクトリに置いた自作ライブラリだけを差し替えます。検索先を不特定の人が書き換えられる場所に設定する運用は避けてください。

差し替えられるのは、互換性が保たれる場合

本章では int answer(void) の名前・引数・戻り値の型を変えず、返す数値だけを変えます。動的側は次に起動したとき新しい実体を使いますが、静的側には以前取り込んだ命令が残ります。

実行中のプロセスが自動で新しいコードへ切り替わる、という実験ではありません。また同じ名前でも、引数や戻り値の受け渡し規則が変われば安全に交換できません。こうしたバイナリ間の約束をＡＢＩと呼びます。動的リンクには更新の利点がある一方、必要なライブラリの配布・検索・互換性を管理する責任があります。

３ハンズオン

準備：コンテナ内で実行する

第１章の手順でリナックスコンテナのシェルへ入り、次を実行します。以下の生成物は一時ディレクトリに置き、教材のソースやシステムのライブラリは変更しません。

cd /workspace/textbook/new/labs/ch12
work=$(mktemp -d /tmp/compilerbook-ch12.XXXXXX)
echo "$work"

mktemp -d は重複しない作業ディレクトリを作り、そのパスを表示します。$(...) でその出力を変数 work に保存しています。同じシェルで順番に進めてください。

実験１：同じ関数から、二種類のライブラリを作る

gcc -std=c11 -Wall -Wextra -c main.c -o "$work/main.o"
gcc -std=c11 -Wall -Wextra -c answer.c -o "$work/answer.o"
ar rcs "$work/libanswer.a" "$work/answer.o"
gcc -fPIC -shared -Wl,-soname,libanswer.so answer.c -o "$work/libanswer.so"
ar t "$work/libanswer.a"

最初の２行はコンパイルとアセンブルを行い、リンク前の .o を作ります。ar rcs は部品をアーカイブへ登録し、名前を検索する索引も作ります。最後の ar t はその中身の名前を一覧にし、answer.o が入ったことを確認します。

-fPIC は、配置場所が変わっても扱える位置独立なコードを生成する指定です。-shared は共有ライブラリを作ります。-soname は、このライブラリの識別名を libanswer.so とします。共有ライブラリをリンクした実行ファイルの依存情報には、この名前が使われます。

実験２：二つの実行ファイルを作り、結果を比べる

gcc "$work/main.o" "$work/libanswer.a" -o "$work/archive-app"
gcc "$work/main.o" -L"$work" -lanswer -Wl,-rpath,'$ORIGIN' -o "$work/shared-app"
"$work/archive-app"
echo $?
"$work/shared-app"
echo $?

部品を必要とする main.o を、ライブラリより前に置きます。特にアーカイブの検索は入力順の影響を受けるので、この順番を保ってください。実行前に、画面に表示される数値と終了状態を別々に予想します。

実行後に開く：何が同じだったか

どちらも７を表示し、終了状態は０です。answer の７を printf が表示し、main の return 0; が成功を示します。echo $? が見るのは直前に実行したプログラムの終了状態で、printf が表示した７ではありません。出力が同じでも、関数の置き場所は異なります。

実験３：ファイル内の参照を読む

nm "$work/archive-app" | grep answer
nm -D "$work/shared-app" | grep answer
nm -D "$work/libanswer.so" | grep answer
readelf -d "$work/shared-app"
readelf -d "$work/archive-app"

nm は名前の表を表示します。-D は動的リンク用の表を選びます。縦棒は左の出力を右へ渡し、grep で answer を含む行だけを選んでいます。静的側は T answer、動的側の実行ファイルは U answer、共有ライブラリ側は T answer を探します。T はコード領域に定義があること、U はそのファイル自身には定義がないことを示します。

readelf -d は動的リンク用の情報を読みます。shared-app の NEEDED に libanswer.so、検索先に $ORIGIN があるか確認します。archive-app に libanswer.so の依存はありませんが、libc.so.6 などの依存があっても矛盾ではありません。

実行後に開く：U が残るのはエラーか

動的リンク用に外部の定義を参照しているため、完成した実行ファイルでも U が残ります。今回なら libanswer.so の定義が解決先です。「ファイル内に定義がない」と「実行できない」は同じではありません。

実験４：共有ライブラリだけを変更する

先に結果を予想します。二つの実行ファイルは作り直さず、answer の返す値だけを４２にした共有ライブラリを作ります。すでに実行したプログラムが終了してから進めます。

sha256sum "$work/archive-app" "$work/shared-app" > "$work/before"
gcc -fPIC -shared -DVALUE=42 -Wl,-soname,libanswer.so answer.c -o "$work/libanswer.so"
"$work/archive-app"
"$work/shared-app"
sha256sum "$work/archive-app" "$work/shared-app" > "$work/after"
cmp "$work/before" "$work/after"

-DVALUE=42 はソース内の VALUE を４２としてコンパイルする指定です。sha256sum はファイル内容の指紋を計算します。その出力を保存し、cmp で変更前後を比較します。一致なら cmp は何も表示せず終了します。

実行後に開く：何が変わり、何が変わらなかったか

archive-app は７、shared-app は４２を表示します。二つの実行ファイル本体は変化していません。違いは、静的側には古い実体が取り込まれ、動的側は今回読み込んだ .so の実体を使うことです。.a の内容も今回は変更していません。

実験５：必要な共有ライブラリが見つからない場合

削除せず、一時的に別名へ移します。動的側が失敗することを確認したら、元の名前に戻します。

mv "$work/libanswer.so" "$work/libanswer.hidden"
"$work/shared-app"
echo $?
"$work/archive-app"
mv "$work/libanswer.hidden" "$work/libanswer.so"
"$work/shared-app"

通常の教材環境では shared-app はライブラリが見つからないというエラーになり、main の表示処理へ到達しません。終了状態は非０です。一方、archive-app は７を表示します。元へ戻すと shared-app は４２を表示します。

失敗を観察するコマンドが含まれるため、この実験を途中で停止する設定のスクリプトへそのまま貼らず、対話シェルで一つずつ実行してください。システムのライブラリには触れません。

教材と同じ観察をまとめて確かめるには bash check.sh を実行します。別の一時ディレクトリで検証し、上の作業には干渉しません。

４理解チェック

二つとも７を表示しただけで、リンク方法が同じと言えるか？

解説を読む

言えません。動作の結果と実体の置き場所は別です。名前の表、NEEDED、差し替え後の動作を組み合わせて判別します。

-L を指定したのに、起動時に .so が見つからないのはなぜか？

解説を読む

-L はビルド時の検索先だからです。起動時の動的リンカーには別の検索規則があります。今回の RUNPATH はそのための設定です。

libanswer.a を更新するだけで、すでに作った archive-app の答えは変わるか？

解説を読む

変わりません。古いコードが取り込まれています。新しいアーカイブと再リンクして実行ファイルを作り直す必要があります。main.c の内容が同じなら main.o を再利用できます。

共有ライブラリの関数名さえ同じなら、引数を増やしても交換できるか？

解説を読む

安全に交換できません。呼び出し側の命令は以前の引数の渡し方のままです。名前の一致だけではＡＢＩの互換性を保証しません。

自作コンパイラが外部関数への call を出せば、.so の探索も担当したことになるか？

解説を読む

いいえ。コンパイラのコード生成、ビルド時のリンク、起動時の読み込みと参照解決は別の役割です。出した参照を、後続の道具と実行環境が結び付けます。
