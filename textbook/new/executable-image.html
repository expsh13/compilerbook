第１１章

実行イメージと初期化

ファイルに保存するものと、起動時・実行中に用意するものを分ける。

第１０章では、文字列を .rodata に置いて、その場所を返しました。今回は、命令やデータが実行ファイルにどう入り、起動後の状態へどうつながるかを調べます。

１この章で扱う問い

変数の初期値は、ファイルに書かれているのか、それとも命令を動かして作るのか？

たとえば、初めから７を持つ変数と、初めは０の大きな配列を考えます。どちらも main から読めますが、その値をファイル内へ同じ方法で保存する必要はありません。また、関数を呼ぶたびに計算する初期値は、別の仕組みで用意します。

本章はリナックス x86-64 のＥＬＦ形式を対象に、既存のＣコンパイラで作ったファイルを観察します。自作コンパイラへ新しい構文は追加しません。動的リンクは入り口だけ示し、共有ライブラリとの詳しい接続は第１２章で扱います。

２この章の理論

一つのプログラムに、違う種類の初期状態を置く

今回の layout.c には、関数の外側に次の定義があります。

const char label[] = "ABC";
int seed = 7;
int zeros;
unsigned char reserve[65536];

label は文字列のバイト列、seed は７から始まる整数です。zeros と reserve は明示的な初期値を書いていません。しかし、関数の外で定義したこれらは静的記憶域期間を持ち、プログラムの実行中ずっと存在します。Ｃの規則により、初期値を省略したこれらの整数や配列要素は０になります。

一方、初期化していない自動ローカル変数が０になる保証はありません。第７章で代入前の読み出しを拒否したことと矛盾しません。名前を書いた場所や記憶域期間が違い、適用する規則が違います。

ファイル内の初期値と、動くときに計算する値を比べるため、次の関数も用意しています。

static void visit(void) {
    static unsigned count;
    int local = seed + (int)++count;
    printf("関数呼び出し：count=%u、local=%d\n", count, local);
}

count は関数内に見える名前ですが、static が付いているため実行中ずっと存在し、最初は０です。visit を呼ぶたびに０へ戻るわけではありません。++count は count を１増やして、その増やした値を使います。(int) は、この小さな値を int として計算する指定です。

local は呼び出すたびに用意される自動ローカル変数です。その宣言を実行するたびに、現在の seed と増やした count から値を求めます。seed が７なら、１回目は８、２回目は９です。関数定義の前の static は、その関数名をこのソースの内部で使う指定であり、変数 count の static とは着目する役割が異なります。

実行ファイルには、内容と配置の情報がある

ＥＬＦは、今回のオブジェクトや実行ファイルで使う形式です。実行ファイルは機械語を先頭から最後まで並べただけのものではなく、入口の位置、命令とデータの場所、読み込み方法などの情報も持ちます。

セクションは、ファイル内の命令やデータを用途別にまとめる区分です。今回のビルドでは、代表的なものは次のようになります。配置はコンパイラやリンカーの選択にも依存するので、すべてのＣの変数が必ずこの表どおりになるという規則ではありません。

セクション今回の内容初期状態の用意
.textmain や visit の命令機械語のバイトをファイルに持つ。
.rodatalabel の ABC と終端、表示用文字列など読み取り専用にするデータのバイトを持つ。
.dataseed の初期値７書き換え可能なデータの初期バイトを持つ。
.bsszeros、reserve、count必要な領域の大きさを記録し、メモリでは０で始める。

.bss は、領域の大きさなどの情報がファイルにない、という意味ではありません。その領域を埋める０のバイト列そのものを、同じ量だけファイルへ保存しなくてよいという違いです。大きなゼロ初期化配列を置いても、その大きさと同じだけ実行ファイルが膨らむ必要はありません。

読み込む単位は、セクションと同じではない

実行の準備で使う主な情報は、プログラムヘッダという表です。この表に記載されるセグメントは、メモリへ配置する範囲などを表します。一つのセグメントに、複数のセクションが含まれることがあります。

特に LOAD は、ファイルのどの範囲を、どの仮想アドレスに、どんなアクセス権で用意するかを表します。読み取りを R、書き込みを W、実行を E と表示する道具を、後で使います。命令を置く範囲と、書き換えるデータを置く範囲は、異なる権限にできます。

FileSiz はその範囲がファイル内で持つバイト数、MemSiz はメモリ側で必要なバイト数です。後者の方が大きい場合、ファイル由来の部分の後ろに、差分を０で用意します。これが今回の .bss を含む領域で観察できる仕組みです。

ここでいうアドレスは、プロセスから見える仮想アドレスです。物理メモリの場所そのものではありません。また「用意する」は、ファイル全体を直ちに別の物理メモリへコピーする、という意味でもありません。実際のページの読み込みなどはＯＳが必要に応じて行えます。この章では、プログラムから見える内容の対応を観察します。

main は、実行ファイルの入口そのものではない

通常のＣプログラムでは、main より前に起動処理があります。ＥＬＦにはエントリポイントという、実行を開始するための位置が記録されています。今回のプログラムでは、その位置は _start という起動用コードに対応します。main の位置とは異なります。

さらに今回の実行ファイルは動的リンクを使い、INTERP に指定された動的リンカーの起動処理も関わります。その場合、ＣＰＵが最初からこの実行ファイルの _start に入る、と単純化してはいけません。必要な共有ライブラリなどの準備をした後、プログラム側の入口へ進みます。

スタックも実行環境の一部として用意されます。第７章の自動ローカル変数の値は、あらかじめ .data にすべて並べられているのではなく、関数が動くときに必要な計算や保存を行います。プログラムによっては main より前に動く初期化関数もありますが、すべての初期化を main より前にまとめて行うわけではありません。

実行中の変更は、元の初期値を書き換えるのか

main 内で seed を４２に変えると、現在の実行中の値は４２になります。しかし、この代入だけでディスク上の実行ファイル内の７が４２に書き換わることはありません。今回の通常のデータ領域は、実行中の変更をそのまま元ファイルへ保存するための領域ではないからです。

同じ実行ファイルをもう一度起動すれば、新しい実行では再び seed は７、zeros と count は０から始まります。状態を次の実行へ残したいなら、ファイルやデータベースなどへ保存する別の処理が必要です。

「初期化」という言葉だけでまとめず、①ファイルに初期バイトを持つ、②実行環境がゼロ領域を用意する、③実行するたびに式を計算する、を区別します。Ｃの static な変数に任意の関数呼び出しを初期値として書ける、という意味でもありません。本章の静的な初期値は定数です。

３ハンズオン

準備：観察しやすい実行ファイルを作る

これまでと同じリナックスのコンテナ内で実行します。まだ入っていなければ、マック側のリポジトリで make -f docker.mk shell を実行します。

cd /workspace/textbook/new/labs/ch11
gcc -std=c11 -Wall -Wextra -O0 -fno-common -fno-pie -no-pie layout.c -o /tmp/ch11-layout

-O0 は最適化を抑える指定です。-fno-common は今回の未初期化の大域変数を共通シンボルとして扱わない指定、-fno-pie -no-pie は観察のため、位置独立実行ファイルという形式を使わずに作る指定です。この教材の出力にだけ適用し、システム全体の設定を変えません。一般の製品でこの設定を推奨しているわけでもありません。

実験１：開始時と、関数を呼んだ後の値を比べる

実行前に：seed、zeros、reserve の先頭と末尾、２回呼んだ visit の count と local を予想してください。

/tmp/ch11-layout
echo $?
実行後に開く：３種類の準備が見える

開始時は seed が７、zeros が０、reserve の要素も０です。visit の１回目は count=1・local=8、２回目は count=2・local=9。最後に main が seed を４２、zeros を９、reserve の末尾を１へ変えた表示が出ます。終了状態は main が返す０で、表示中の４２などとは別です。

reserve のサイズは６５５３６バイトです。教材は全要素が０であることを assert で検査し、表示は先頭と末尾だけに絞っています。count が２回目に２であることから、static の変数が呼ぶたびに作り直されていないことも確認します。

実験２：変数が、どのセクションにあるか調べる

nm -S /tmp/ch11-layout
readelf -SW /tmp/ch11-layout

nm の -S はシンボルの大きさも表示します。出力から seed、zeros、reserve、label を探してください。第６章の T に加えて、D は初期値を持つデータ、B はゼロ領域、R は読み取り専用データに対応します。表示の数値は１６進です。

readelf はＥＬＦの構造を見る道具です。-S はセクション表、-W は１行を折り返さず広く表示する指定です。.bss の種類にある NOBITS を探します。

観察後に開く：ファイルに中身を持たない領域

今回の設定では seed は D、zeros と reserve は B、label は R です。.bss は NOBITS、つまり領域のための実データのバイト列をファイルに持たない形式です。count も通常は小文字 b と、補助的な接尾辞の付いた名前で見えます。local はこの表の大域シンボルとしては現れません。

実験３：FileSiz と MemSiz を比べる

readelf -lW /tmp/ch11-layout

小文字の -l はプログラムヘッダの表示です。LOAD の行を探し、FileSiz と MemSiz を比較します。特に RW の行に注目してください。出力の下部には、各セグメントにどのセクションが含まれるかの対応表もあります。

観察後に開く：メモリ側の方が大きい理由

検証環境の書き込み可能な LOAD では、FileSiz が 0x22c、MemSiz が 0x10290 でした。正確な数字は環境で変わります。重要なのは後者が大きいことです。差分には reserve などのゼロ領域や配置上の余白が含まれます。差が reserve の長さと完全一致する必要はありません。

この表は実行中のメモリの内容を読み出したものではありません。「こう配置する」というファイル内の指示を見ています。実験１の実行時の値と組み合わせて、指示と結果の対応を確認します。

実験４：ゼロ配列を大きくしても、ファイルは同じだけ増えるか

gcc -std=c11 -Wall -Wextra -O0 -fno-common -fno-pie -no-pie -DRESERVE=1048576 layout.c -o /tmp/ch11-large
wc -c /tmp/ch11-layout /tmp/ch11-large
size /tmp/ch11-layout /tmp/ch11-large
/tmp/ch11-large

-DRESERVE=1048576 は、ソースが使う配列の長さを変更する指定です。６４ＫｉＢから１ＭｉＢへ増やします。wc -c は実ファイルのバイト数、size は命令・データ・bss などの大きさをまとめて表示します。size の合計は、そのまま実ファイルの長さとは限りません。

実行後に開く：増えるのは主に、実行時に必要な領域

bss は大きくなりますが、ファイルは差分の９８３０４０バイト分も増えません。配列全体の０を保存する代わりに、必要な大きさを記録しているからです。大きい版の実行でも、初めの全要素が０であることを検査します。ファイルが小さいことと、実行時に必要な領域が小さいことは別です。

実験５：実行し直すと、初期値へ戻るか

sha256sum /tmp/ch11-layout
/tmp/ch11-layout
sha256sum /tmp/ch11-layout
/tmp/ch11-layout

sha256sum は、ファイル内容を比較するためのハッシュ値を表示します。実行前後の文字列が一致するか、また２回目の開始時に seed が７か４２かを観察します。

実行後に開く：実行中の状態と、元ファイルの初期値は別

ファイルのハッシュ値は変わらず、２回目も seed は７から始まります。count も最初の呼び出しでは１です。前の実行で値を変更しても、それを次の実行へ保存する処理は書いていないからです。

補足の観察：入口と main の位置を比べる

readelf -h /tmp/ch11-layout
nm /tmp/ch11-layout

-h はＥＬＦヘッダの表示です。Entry point address と、nm の _start・main の値を比べます。検証環境では入口が 0x401070、_start も同じで、main は別の位置でした。先頭の０の数や 0x の有無は表示上の違いです。

実験３の INTERP には動的リンカーのパスも出ます。非ＰＩＥで作っていても、共有ライブラリを使わない静的リンクという意味ではありません。この区別を次章で扱います。

全体を確認する 検証スクリプトは、コンテナ内の第１１章フォルダで bash check.sh と実行できます。初期値・再実行・ファイルの不変・配置情報と、大きい配列の結果を確認します。

４理解チェック

.bss が NOBITS なら、その変数は実行中にも存在しないか？

解説を読む

存在します。０で始める領域の実データをファイルに格納しないだけで、メモリ側には必要な領域を用意します。大きさや配置の情報は残っています。

セクション表だけが、ＯＳの読み込み指示なのか？

解説を読む

違います。読み込みは主にプログラムヘッダのセグメント情報を使います。セクションは命令やデータの区分で、複数のセクションが一つの LOAD に入る場合があります。

関数内の static count と自動変数 local は、いつ初期化されるか？

解説を読む

今回の count は静的記憶域期間を持ち、初めは０で、呼び出し間でも値を保ちます。local の初期化式は、その宣言に到達するたびに実行します。名前がどちらも関数内にあっても、存続期間は同じではありません。

大域変数が０になるなら、初期化していない自動変数も０か？

解説を読む

その保証はありません。静的記憶域期間の初期化規則を、自動ローカル変数に当てはめてはいけません。未初期化の値を読んで偶然の結果を確かめる実験はしません。

seed=42 を実行した後、元の実行ファイルも４２を初期値に持つか？

解説を読む

いいえ。今回の代入は実行中のデータを変えるだけです。元ファイルに保存する別の処理がなければ、新しい実行では元の初期値７から始まります。

main がエントリポイントではないのはなぜか？

解説を読む

Ｃの関数として main を動かす前に、実行環境や起動処理が必要だからです。今回の実行ファイルの入口は _start で、その前に動的リンカーの準備もあります。main から戻った後にも終了処理が続きます。
