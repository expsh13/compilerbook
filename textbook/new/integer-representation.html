第９章

整数の表現

ビット列だけでなく、何ビットを、どの規則で読むかを見る。

これまでの章では、小さな整数を中心に実験してきました。今回は、負の値や幅の違いを正面から扱います。コンパイラの構文を増やすのではなく、その出力した命令が扱う値の意味を確かめる章です。

１この章で扱う問い

同じビット列なのに、２５５にも－１にも見えるのはなぜか？

第５章では、3-5 の結果を終了状態で見ると２５４になりました。計算を間違えたのでしょうか。それとも、値を見る途中で幅や解釈が変わったのでしょうか。数がレジスタに入り、幅を変え、最後に観測されるまでを分けて考えます。

前提はレジスタとメモリ、第８章の整数の引数・戻り値です。図では８ビットに縮めて説明しますが、対象のＣＰＵはこれまでと同じ x86-64 です。ビットの並びは左を上位、右を下位として描きます。メモリ上のバイトの並び順を表す図ではありません。

２この章の理論

まず、ビットの位置に重みを付ける

１ビットは０か１です。２ビットなら４通り、８ビットなら２の８乗で２５６通りの並びがあります。８ビットを符号なし整数として読むと、０〜２５５を表せます。右端から１、２、４、８、１６、３２、６４、１２８という重みを付け、１の位置の重みを足します。

負の整数は、２の補数で表す

今回の機械では、符号付き整数に２の補数という表現を使います。８ビットなら、最上位の重みを－１２８とし、残る７ビットは従来どおりの正の重みにします。最上位が０なら０〜１２７、１なら－１２８〜－１です。最上位ビットを単なる「マイナス記号」とし、残りを絶対値として読む方式ではありません。

８ビットの並びをいったん符号なしの数 u と読んだ場合、u が１２８未満なら符号付きでも同じ値です。１２８以上なら、u−２５６が符号付きの値になります。11111110 は２５４なので、２５４−２５６＝－２です。

負数のビット列を作るには、対応する正数のビットを反転して１を足す方法も使えます。２の 00000010 を反転すると 11111101、１を足すと 11111110 になり、－２を表します。幅を８ビットと決めて操作している点が大切です。

ビット幅符号なし２の補数の符号付き
８０〜２５５－１２８〜１２７
３２０〜２の３２乗−１－２の３１乗〜２の３１乗−１
６４０〜２の６４乗−１－２の６３乗〜２の６３乗−１

符号付きでは負の側が一つ多く、－１２８に対応する正の１２８は８ビットの符号付きには入りません。そのため、最小値の符号を反転する操作も、同じ幅に収まるとは限りません。

幅を広げるとき、上に何を足すか

８ビットの 11111111 を１６ビットにするとき、上へ０を足すと２５５のままです。これはゼロ拡張です。一方、－１という符号付きの値を保つには、元の最上位ビットと同じ１を上へ足します。これを符号拡張と呼びます。

符号拡張では、元の最上位が０なら０、１なら１を補います。負数だけの特別操作ではありません。実験で使う movsx rax, dil は符号拡張、movzx eax, dil はゼロ拡張です。dil は第８章で引数に使った rdi の下位８ビットを指します。

ゼロ拡張の行が eax 宛てなのは、x86-64 で eax に書くと、rax の上位３２ビットも０になるからです。dil から eax へのゼロ拡張と合わせて、rax 全体では６４ビットの正の２５５になります。第５章の cqo も、割り算に必要な幅へ値の意味を保って広げる、符号拡張の一種でした。

rax・eax・al は、別々の箱ではない

rax は６４ビット全体、eax はその下位３２ビット、al はさらに下位８ビットの名前です。同じ保存場所の一部分を指します。ただし、「その部分を読む」ことと「そこへ書いたときの効果」は分けて考えます。

図は１６進数で、１桁が４ビット、f は 1111 を表します。８桁で３２ビット、１６桁で６４ビットです。eax を読んだだけでは上位ビットは変わりません。また、al や１６ビットの ax への書き込みには、eax のように上位全体を０にする効果はありません。

幅を超えた足し算では、何が残るか

８ビットの機械語の加算で２５５に１を足すと、数学的な結果２５６は９ビット必要です。結果の下位８ビットだけを残すと０になります。同じ命令で１２７に１を足すと、結果のビット列は 10000000 です。符号なしなら１２８で収まりますが、８ビットの符号付きとして読むと－１２８になり、期待した正の１２８は表せません。

ＣＰＵには、こうした計算の状態を記録するフラグがあります。今回観察する CF は符号なしの加算で幅の外へ桁が出たか、OF は符号付きの加算として範囲を超えたかを示します。１ならその条件が成立、０なら不成立です。

８ビットで行う操作結果のビットＣＦＯＦ
２５５＋１（符号付きでは－１＋１）00000000１０
１２７＋１10000000０１

add に「符号あり」という型情報を渡しているわけではありません。同じビット加算に対して両方のフラグが更新され、後の処理が必要な条件を使います。今回の検証用関数は add al, 1 の直後に setc と seto でフラグを０か１の値に取り出します。フラグを変える別の計算を挟む前に記録する必要があります。

機械語の動きと、Ｃの規則を混ぜない

機械語の８ビット加算を見て、Ｃのどんな整数加算も同じように折り返す、と考えてはいけません。Ｃの符号付き整数の加算などで表現範囲を超えると、通常は未定義動作です。言語として結果を保証せず、コンパイラはその事態が起きない前提で最適化できます。「負になるはず」も「必ず止まるはず」も保証されません。本章では、その動作に依存するＣの実験はしません。

一方、Ｃの符号なしの型への整数変換は、その型の幅に対応した２のべき乗を法とする値になります。８ビットの符号なしへ３００を変換すれば４４です。ただし、８ビットの型で宣言した変数の式が、常に８ビットで計算されるわけでもありません。

uint8_t a = 255;
int sum = a + 1;
uint8_t narrowed = (uint8_t)sum;

uint8_t は、この環境で使える８ビットの符号なし整数型です。この例の a は加算時に int へ整数昇格するため、a+1 は int の２５６として計算されます。３行目の (uint8_t) は型変換の指定で、ここで８ビットへ狭めた結果が０になります。加算で０になったのか、後の変換で０になったのかを分けて読んでください。

計算結果、返り値、終了状態を区別する

これまでの実験は、生成した main の返り値をシェルの $? で観察していました。この経路では、一般に使える計算結果の全体ではなく、終了状態の下位８ビットを見ています。３００なら４４、－２なら２５４です。これは、どんな命令も８ビットで計算していたという意味ではありません。

この違いを確かめるため、今回は printf で値そのものも表示します。表示は文字列を画面へ送る処理、return は値を呼び出した側へ返す処理です。画面に３００が出た直後でも、echo $? は４４を表示できます。

第７・８章の自作言語に、符号なし型や８ビット型を追加するわけではありません。これまでの値は６４ビットの命令で扱っていました。今後型に応じたコードを作るには、幅・符号・拡張方法・範囲超過の規則を言語として決める必要があります。

３ハンズオン

準備：観察用プログラムを作る

第１章と同じリナックスのコンテナ内で実行します。まだ入っていなければ、マック側のリポジトリで make -f docker.mk shell を実行してください。

cd /workspace/textbook/new/labs/ch09
gcc -std=c11 -Wall -Wextra -o /tmp/ch09-inspect inspect.c integers.s

inspect.c は数値とビット列を表示するＣのプログラム、integers.s は観察する機械語の関数です。gcc がそれぞれをコンパイル・アセンブルし、リンクして一つの実行ファイルにします。これは自作コンパイラではなく、整数の振る舞いを調べる道具です。

表示コードの PRIu64 などは、６４ビット整数を正しい形式で printf に渡すための指定です。今回の中心は、表示の実装を暗記することではなく、何の幅・符号の値を観察しているかを説明できることです。

実験１：同じ並びを二通りに読む

実行前に：01111111、10000000、11111110、11111111 を、それぞれ符号なしと２の補数で読んだ値をメモします。

/tmp/ch09-inspect bits

bits は、このプログラムへ渡す実験名です。表示側は、符号付きへの範囲外変換の結果に頼らず、「１２８以上なら２５６を引く」という規則で解釈を計算しています。メモリの型を動的に切り替えているわけではありません。

実行後に開く：ビットは同じでも値は違う

順に、符号なしでは１２７・１２８・２５４・２５５、符号付きでは１２７・－１２８・－２・－１です。最上位ビットが０の最初の例だけ、両者の値が一致します。

実験２：ゼロ拡張と符号拡張を動かす

引数の下位８ビットに 11111111 を用意して、２種類の機械語関数へ渡します。６４ビットへ広げた後の値と、１６進表記を予想してください。

/tmp/ch09-inspect extend
実行後に開く：２５５を保つか、－１を保つか

ゼロ拡張は値２５５、１６進で 00000000000000ff。符号拡張は値－１、１６進で ffffffffffffffff です。符号拡張の表示では、符号付きの戻り値を十進で表示し、同じ２の補数表現に対応する符号なし値へ変換して１６進も表示しています。

この結果は、引数全体の２５５を符号付きのまま広げたものではありません。関数が最初に下位８ビットだけを見て、その最上位を符号として拡張した結果です。どの幅から拡張したかを言葉にしてください。

実験３：eax への書き込みを見る

mov rax, -1 の後に mov eax, 1 を実行します。rax の上位３２ビットが残るかを予想してから実行します。

/tmp/ch09-inspect register
実行後に開く：rax 全体も１になる

上位３２ビットは０になるので、rax 全体の値は１です。eax は独立した別レジスタではなく、書き込みには上位を０にする効果があります。

命令を確かめたい場合は、次のコマンドでこの関数だけを逆アセンブルできます。-d は機械語の表示、-Mintel は本書の記法、最後の指定は関数名です。

objdump -d -Mintel --disassemble=write_eax /tmp/ch09-inspect

実験４：加算の桁あふれと、Ｃの変換を比べる

まず、２５５＋１と１２７＋１を add al, 1 で行います。結果のビットと、ＣＦ・ＯＦの０／１を予想してください。

/tmp/ch09-inspect add
実行後に開く：二つの「範囲を超える」

２５５＋１は結果０・ＣＦ１・ＯＦ０、１２７＋１は結果１２８・ＣＦ０・ＯＦ１です。結果欄は下位８ビットを符号なしで表示しているため、後者は１２８と出ます。符号付きとして解釈すると－１２８です。

次に、理論で見た uint8_t a=255 のＣの例を動かします。加算直後の sum と、狭めた後の narrowed が同じか予想します。

/tmp/ch09-inspect convert
実行後に開く：計算した幅と、保存した幅が違う

sum は２５６、８ビットへ変換した後は０です。Ｃの式の型の規則があるため、変数 a の宣言だけを見て「８ビットの加算命令と同じ」とは言えません。

実験５：表示した値と、終了状態を同時に見る

exit-value.c は、返す値を printf で表示してから、同じ値を main から返すプログラムです。最初は３００を使います。

gcc -std=c11 -Wall -Wextra -o /tmp/ch09-exit exit-value.c
/tmp/ch09-exit
echo $?
実行後に開く：３００と４４が両方見える

プログラム自身は「main が返す値=300」と表示します。直後の echo は４４を表示します。main の int が３００を表せないのではなく、終了状態を受け取る経路で下位８ビットを見るためです。

次は返す値を－２に変えてビルドします。-DRESULT=-2 は、ソース内の RESULT というマクロを－２として処理する指定です。ソースファイルを書き換えずに、実験する値を変更できます。

gcc -std=c11 -Wall -Wextra -DRESULT=-2 -o /tmp/ch09-exit exit-value.c
/tmp/ch09-exit
echo $?
実行後に開く：－２の下位８ビットは２５４

プログラムの表示は－２、シェルで見る終了状態は２５４です。下位８ビットは 11111110 で、終了状態としては０〜２５５の値で見えます。第５章で見た現象と同じです。

終了状態を確認するときは、対象のプログラムの直後に echo $? を実行します。別のコマンドを挟むと、その別のコマンドの終了状態に変わります。

全体の検証は、第９章のフォルダで bash check.sh と実行できます。検証スクリプトは最適化なしと最適化ありの両方で表示を確認し、３００と－２の終了状態も確かめます。

４理解チェック

11111111 だけを見て、値は－１だと言い切れるか？

解説を読む

幅と解釈が必要です。８ビットの２の補数なら－１、８ビットの符号なしなら２５５です。より広い値の下位８ビットだけを抜き出した図かもしれません。

８ビットの－２をゼロ拡張すると、－２のままか？

解説を読む

いいえ。元の下位８ビットは２５４を表す並びなので、上を０で埋めると正の２５４になります。負の値を保って幅を広げたいなら符号拡張が必要です。

ＣＦが０なら、符号付きの計算にも範囲超過はないか？

解説を読む

いいえ。８ビットの１２７＋１ではＣＦは０ですが、符号付きの正の１２８は入らないためＯＦは１です。どの解釈の範囲を調べるかで、使う条件が違います。

eax を読むだけで、rax の上位３２ビットは０になるか？

解説を読む

なりません。ここで説明した効果は eax への書き込みです。下位だけを読む操作と、書き込みによって全体に起こる変化を分けます。

Ｃの符号付き加算で範囲を超えたら、必ず負になるか？

解説を読む

保証されません。通常のＣでは符号付き加算の範囲超過は未定義動作です。ＣＰＵの加算命令の結果だけから、Ｃのソースの振る舞いを決め付けてはいけません。

終了状態が４４なら、計算結果が４４だったと断定できるか？

解説を読む

できません。３００など、下位８ビットが同じ値も４４に見えます。値全体を確認するなら、今回のように、適切な型の値を表示する観察手段が必要です。
