第１３章

Ｃの型の構文

記号を順に眺めるのではなく、名前にどんな型が組み合わさっているかを読む。

第１０章ではポインタと配列を使い、第１２章では関数の受け渡しの約束を確認しました。今回は、それらをＣの宣言でどう書き分け、コンパイラがどう構造として扱うかを考えます。

１この章で扱う問い

int *a[3];
int (*p)[3];

どちらも int と * と [3] を使うのに、なぜ違う型になるのか？最初は「ポインタを３個並べた配列」、次は「整数３個の配列を指すポインタ」です。括弧によって結び付きが変わります。この違いを、読み方だけでなく、使える式や大きさでも確かめます。

本章ではＣ１１の宣言のうち、int、ポインタ、固定長配列、関数、const、typedef を扱います。既存のＧＣＣで観察し、自作コンパイラへの実装は行いません。宣言の構文木から型を組み立てる考え方までを示し、構造体や可変長配列などの全構文は扱いません。

２この章の理論

型の出発点と、名前に付く形を分ける

int *p;
int *p, q;

１行目の int は型の出発点、*p は名前とポインタの形を指定する宣言子です。組み合わせると、p は int を指すポインタになります。２行目では宣言子が *p と q の二つあるため、p だけがポインタで、q は int です。これは独立した例で、同じ場所へ２行とも書く指示ではありません。

型は単なる「整数かどうか」の印ではありません。ポインタなら何を指すか、配列なら何が何個並ぶか、関数なら引数と戻り値が何か、という内側の型を含みます。コンパイラはこの情報を使い、必要な大きさや、代入・呼び出しが適切かを判断します。

名前から、結び付きの強い部分を読む

本章の宣言では、名前から出発し、同じ括弧の範囲にある右側の [] や関数の () を、左側の * より先に読みます。グループを作る括弧に囲まれている場合は、その内側の結び付きを先に読み、外へ進みます。最後に int へつなぎます。

int *a[3]; なら、a → [3] → * → int。「a は３要素の配列、その要素はポインタ、その指す先は int」です。一方 int (*p)[3]; では、p は括弧の内側にあるので p → * → [3] → int。「p はポインタ、その指す先は３要素の配列、その要素は int」です。

これは宣言を読む順序です。実行時に配列やポインタが順番に作られる、という意味ではありません。宣言中の * は型を指定する記号、式の中の * はポインタが指すものを取り出す演算子で、役割を区別します。

型が違うと、使う式も違う

int values[3] = {10, 20, 30};
int *a[3] = {&values[0], &values[1], &values[2]};
int (*p)[3] = &values;

a[1] はポインタなので、*a[1] で２０を読みます。p は配列へのポインタなので、まず *p で配列を取り出し、(*p)[1] で２０を読みます。宣言の括弧は、必要な操作の組み合わせにも現れます。

sizeof a はポインタ３個分、sizeof p はポインタ１個分、sizeof *p は int ３個分です。教材のリナックス x86-64 環境では順に２４、８、１２バイトになります。この数値はＣのあらゆる環境で共通ではありません。

配列 values は多くの式で先頭要素へのポインタへ変換されますが、&values は配列全体へのポインタです。アドレスの出発点が重なっていても型は異なり、int へのポインタの +1 は int １個分、配列へのポインタの +1 は配列１個分進みます。１個先の終端を指すことと、そこを読み書きしてよいことは別です。

関数そのものか、関数を指す変数か

int *f(int x);
int (*fp)(int);

最初は f → (int x) → * → int。f は int を１個受け取り、int へのポインタを返す関数です。関数本体をまだ書いていない宣言です。次は fp → * → (int) → int。fp は int を１個受け取って int を返す関数へのポインタ変数です。引数の名前はこの宣言では省略しています。

たとえば int twice(int x) { return x * 2; } があれば、int (*fp)(int) = twice; と置けます。関数名が関数へのポインタとして使われ、fp(7) でその関数を呼び出せます。これも呼び出しなので、引数と戻り値の型が一致している必要があります。

Ｃ１１で引数なしを明示するなら int f(void); と書きます。宣言の int f(); は引数の型や個数の情報を指定していない形で、同じ意味ではありません。本章では (void) を使います。

const は、どの部分を変更できなくするのか

const int *p;
int *const q = &value;

この２行は型の説明用で、２行目は int 型の value がすでにあるものとします。p は「const int へのポインタ」です。p 自体は別の場所へ向けられますが、*p = 9; のように p を通じて値を書き換えることはできません。指す元の変数が必ず読み取り専用という意味ではなく、この型を通じた書き込みを制限します。

q は「int への const ポインタ」です。q が保持するアドレスを後から変える代入はできませんが、指す先が変更可能な int なら *q = 9; は可能です。const が int に付くか、ポインタに付くかを見分けます。

typedef は、読めた型に名前を付ける

typedef int (*Operation)(int);
Operation op = twice;

最初の宣言を Operation → * → (int) → int と読んだ型に、Operation という別名を付けます。関数ポインタ型の別名なので、２行目の op は関数ではなくポインタ変数です。別名を付けても、受け渡しの規則が別の型へ変わるわけではありません。

コンパイラでは、文字列ではなく型の構造にする

第４章で式を構文木へ変換したように、宣言にも入れ子の構造が必要です。次は本章の説明用に絞った文法です。識別子は変数や関数の名前、宣言指定部はここでは int などの型の出発点を意味します。

宣言     = 宣言指定部 宣言子 ";"
宣言子   = "*"* 直接宣言子
直接宣言子 = (識別子 | "(" 宣言子 ")") 接尾部*
接尾部   = "[" 整数 "]" | "(" 引数型の並び ")"

この文法表の引用符は実際の記号を表し、引用符の外の * は「０回以上の繰り返し」、縦棒は「どちらか」を表します。初期値、複数の宣言子、const などは省いた簡略形です。引数型の並びには void による引数なしの指定も含めて考えます。

処理では、名前から外へ読んだ順序を残します。a の例は「配列３個、ポインタ」、p の例は「ポインタ、配列３個」です。次に int から始め、そのリストを逆順に適用して包みます。単に左から見つけた記号順に型を足すと、括弧の意味を失います。

実装上は、ポインタ型には指す先の型、配列型には要素の型と個数、関数型には戻り値と引数の型の一覧を持たせます。構文解析後にも検査が必要です。Ｃでは「関数の配列」や「配列そのものを返す関数」は許されません。「関数へのポインタの配列」や「配列へのポインタを返す関数」なら表現できます。

関数の引数にある配列宣言は、特別な調整を受ける

void change(int a[3]);

この引数 a の型は、関数の型を決める段階で int * に調整されます。配列３個分が値として丸ごと渡されるのではありません。また、この [3] だけで実行時の長さ検査が入るわけでもありません。

呼び出し側で change(values) と書くと、配列式 values が先頭要素へのポインタに変換されます。「宣言で引数の型を調整すること」と「呼び出しで配列式を変換すること」は別の規則ですが、この例では組み合わさって働きます。配列全体へのポインタを渡したいなら int (*p)[3] と宣言し、&values を渡します。

３ハンズオン

準備：リナックスコンテナのシェルへ入る

第１章の実行環境を使います。下の cd は教材のソースがある場所へ移動し、mktemp は実行ファイル用の一時ディレクトリを作ります。同じシェルで順に進めます。

cd /workspace/textbook/new/labs/ch13
work=$(mktemp -d /tmp/compilerbook-ch13.XXXXXX)

実験１：型から、大きさと操作を予想する

types.c の a、p、fp、op、result の宣言を読み、それぞれ配列・ポインタ・関数のどれかをメモします。特に sizeof a、sizeof p、sizeof *p の違いを予想してから実行します。

gcc -std=c11 -Wall -Wextra -Werror -pedantic types.c -o "$work/types"
"$work/types"
echo $?

ＧＣＣでＣソースから実行ファイルを作り、次の行で動かしています。-std=c11 は規格、-Wall -Wextra は警告、-pedantic は規格に沿った診断を求め、-Werror は警告をエラーとして扱う指定です。-o は出力先です。

実行後に開く：型と結果の対応

最初は２０と２０、大きさは２４・８・１２、最後は１４・１４・２０です。fp と op は同じ twice を呼びます。result は identity が受け取ったポインタを返したものなので、values[1] を指しています。表示した数値と終了状態は別で、main は０を返します。

実験２：括弧を変えると、どこで意味が変わるか

元ファイルを残すため作業コピーを作ります。コピー内の int (*p)[3] = &values; だけを int *p[3] = &values; に変えてください。どの型へ変わり、なぜ同じ初期値を使えなくなるかを先に説明します。

cp types.c "$work/changed.c"
gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only "$work/changed.c"

cp の後、２行目を実行する前に編集します。コンテナにエディタがなければ cp types.c changed.c として教材ディレクトリ内にコピーを作り、マック側のエディタで編集して、検査対象を changed.c に変えられます。-fsyntax-only は実行ファイルを作らず、構文や型などを検査する指定です。

確認後に開く：想定する失敗

p はポインタ３個の配列になり、配列全体へのポインタである &values をそのまま初期値にはできません。診断文はＧＣＣの版で変わります。コンパイル失敗を確認する実験なので、古い実行ファイルを動かして変更後の結果と思わないようにします。

実験３：引数の配列が、コピーではないことを確かめる

parameters.c では change が２番目の要素を９９へ、row が３番目を７７へ変更します。呼び出し後に元の配列がどうなるか予想します。

gcc -std=c11 -Wall -Wextra -Werror -pedantic parameters.c -o "$work/parameters"
"$work/parameters"
実行後に開く：二つの受け取り方

呼び出し元の配列は１２バイト、表示した int * の大きさは８バイトです。変更後は１０・９９・７７です。change の引数は int * に調整され、row の引数は配列へのポインタです。どちらも元の配列に関係するアドレスを受け取るので、元の要素が変わります。

さらに change の引数表記だけを int *a に変えて再ビルドし、結果が変わらないことを確認してください。これは引数の宣言に限る調整であり、関数の外にある配列変数の宣言もポインタに変わる、という意味ではありません。

実験４：読める構文でも、許されない型がある

rejected.c には条件別の不正な宣言があります。-D は検査対象を選ぶ印を定義し、#if によって該当する箇所だけをＧＣＣへ渡します。どれも実行せず、診断を観察します。

gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only -DARRAY_OF_FUNCTIONS rejected.c
gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only -DRETURN_ARRAY rejected.c
gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only -DPOINTER_TYPE rejected.c

順に int f[3](void);、int f(void)[3];、int **p = &a; を検査します。最後の a は int の３要素配列です。診断を読む前に、各宣言を日本語の型へ読み替えます。

確認後に開く：拒否の理由

最初は関数の配列、次は配列を返す関数で、どちらもＣでは許されません。最後は int ** と int (*)[3] の不一致です。配列へのポインタは、ポインタ変数を指すポインタとは違います。キャストで診断を消すのではなく、意図した構造に宣言を合わせます。

実験５：const の位置を確かめる

gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only -DCONST_VALUE rejected.c
gcc -std=c11 -Wall -Wextra -Werror -pedantic -fsyntax-only -DCONST_POINTER rejected.c

最初は const int * を通した値の書き込み、次は int *const 自体への代入です。どの部分が変更禁止なのかを、実際の診断箇所と対応付けます。対話シェルで１行ずつ実行し、エラーを観察してください。

すべての正常例と、５種類の拒否例をまとめて検証するには bash check.sh を実行します。型の大きさの検証は教材のリナックス x86-64 環境を前提としています。

４理解チェック

int *a[3] と int (*a)[3] は、何が３個なのか？

解説を読む

前者は a 自身がポインタ３個の配列です。後者は a が指す先に int ３個の配列があります。a 自身はポインタ１個です。

int (*handlers[2])(int) は何か？

解説を読む

handlers → [2] → * → (int) → int と読みます。int を受け取り int を返す関数へのポインタが、２個並んだ配列です。関数そのものの配列ではありません。

宣言の文字列をそのまま保存するだけで、p+1 を生成できるか？

解説を読む

少なくとも指す先の型と大きさを判断する必要があります。型の構造を持たせれば、ポインタ型から参照先へたどり、１要素分の移動量を計算できます。配列へのポインタなら配列全体の大きさです。

引数 int a[3] は、要素が３個あることを実行時に確認するか？

解説を読む

この表記だけでは確認しません。引数はポインタ型へ調整されます。要素へアクセスする側は、有効な範囲を別途守る必要があります。

const int *p の p を別のアドレスへ変えてもよいか？

解説を読む

はい。const が付くのは指す先の int です。p 自体を固定するなら int *const p の形になります。
