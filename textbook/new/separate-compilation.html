第６章

分割コンパイルとリンク

別々に作った部品の「この関数を使いたい」と「ここにある」を結び付ける。

前章では、自作コンパイラの出力を gcc に渡して実行ファイルにしました。その一回のコマンドに隠れていた、アセンブルとリンクを分けて観察します。今回は自作コンパイラに機能を足すのではなく、その出力側を支えている既存の道具を調べます。

１この章で扱う問い

別のファイルにある関数の場所が、まだわからないのに、呼び出す側の機械語を作れるのはなぜか？

一つのプログラムを複数のファイルに分けると、呼ぶ側と呼ばれる側を別々に作れます。その時点では相手の最終的な位置が決まっていません。そこで「後で結び付けるための情報」を機械語と一緒に残します。この情報を使って部品をつなぐ工程がリンクです。

第１章の call と ret、第２章の gcc の役割が前提です。本章では、Ｃで書いた呼び出し側と、アセンブリで書いた小さな関数を結びます。引数の配置など、関数呼び出しの詳しい規則は第８章で扱います。

２この章の理論

まず、二つの部品を見る

呼び出す側の main.c は、answer という関数を呼び、受け取った値を返します。

#include "answer.h"

int main(void) {
    return answer();
}

answer.h の中心は、次の１行です。

int answer(void);

これは関数の宣言です。「名前は answer、引数はなく、int の値を返す」とＣコンパイラへ知らせます。末尾がセミコロンで、計算をする本体はありません。#include は、コンパイルの前処理でヘッダの内容を取り込みます。関数の機械語を取り込む指示ではありません。

ヘッダの #ifndef から #endif は、同じ内容が繰り返し取り込まれるのを防ぐ囲いです。今回注目するのは、関数の名前と型を伝える宣言の役割です。

呼ばれる側の answer.s には、その関数の定義、つまり実際に動く本体を置きます。主要な部分は次のとおりです。

.intel_syntax noprefix
.text
.globl answer
answer:
    mov rax, 14
    ret

answer: は、この位置に付ける名前です。.globl answer は、その名前を別の部品からも参照できるようにします。関数が呼ばれると、mov が返す値１４を用意し、ret が呼び出した側の続きへ実行を戻します。Ｃの int の返り値としては下位３２ビットの eax が使われ、この例では１４になります。

実際のファイルには、関数であることを記す .type と、関数のバイト数を記す .size もあります。.-answer は現在位置から関数の開始位置を引いた長さです。末尾の .note.GNU-stack は実行可能なスタックを要求しないという情報です。これらはＣＰＵが実行する計算命令ではなく、ツールが使う付随情報です。

オブジェクトファイルという、結合前の形で止める

分割コンパイルでは、ソースを別々に処理してオブジェクトファイルを作り、それらを後でリンクします。本章の .o は、機械語だけでなく、定義した名前、外部に求める名前、後で調整する箇所などを持つファイルです。そのまま起動して使う実行ファイルではありません。

gcc -c main.c の -c は、リンクを行わずオブジェクトファイルで止める指定です。Ｃからのコンパイルとアセンブルは行います。一方、gcc -c answer.s は、すでにアセンブリなのでアセンブルを行います。-o は出力名の指定で、実行ファイルにするという意味ではありません。

シンボルは、名前と場所を結び付ける情報

シンボルは、関数などの名前を、位置や属性と結び付けて扱うための情報です。オブジェクトファイルのシンボル表を見ると、「この部品が定義している名前」と「使うが、この部品内では未定義の名前」を区別できます。

main.o は main を定義していますが、answer の本体は持ちません。answer.o は逆に、answer の本体を持ちます。リンカーはこれらを照合して、呼び出し側が求めている answer をどの定義につなぐか決めます。この仕事をシンボル解決と呼びます。

本章の通常のＣの名前について、リンカーは主にシンボル名を照合します。ヘッダに書いた型と、アセンブリの実装が本当に一致するかまで保証するわけではありません。名前が合うことに加えて、引数や返り値の受け渡し規則も一致させる必要があります。

名前が見つかったら、参照する箇所を調整する

定義が見つかっても、まだ仕事が残っています。リンカーは部品の命令やデータを配置し、その配置に合わせて、参照を含む箇所の数値を調整します。この処理を再配置と呼びます。

本章の call は、次の命令の位置から呼び出し先までの距離を機械語に持つ形です。main.o を作る時点では、別の部品にある answer までの距離はわかりません。そこでアセンブラは、命令と一緒に「この位置の数値を、answer の位置に基づいて調整してほしい」という再配置情報を残します。

すべての参照が同じ形式とは限りません。ここでは自分たちの二つの部品の間の呼び出しに絞ります。共有ライブラリとの接続など、起動時や実行中まで残る処理は第１２章で扱います。

部品が足りない場合と、重複する場合

main.o だけを渡すと、今回の answer の定義がなく、リンクは失敗します。典型的な表示が undefined reference、つまり「参照先の定義が見つからない」です。.o の段階で未定義の名前を持つこと自体は正常ですが、今回の実行ファイルを作るにはその相手が必要です。

反対に、同じ外部向けの関数 answer を定義した通常のオブジェクトを二つとも渡すと、multiple definition、つまり「定義の重複」で失敗します。今回は先勝ちで選ぶ仕組みではありません。ライブラリや特別なシンボル属性の規則は、この実験には持ち込みません。

前章とのつながり

第５章の gcc -o 実行ファイル アセンブリ.s も、内部ではアセンブルの後にリンクしていました。自作したのは式を命令へ変える部分であり、リンカーまで自作していたわけではありません。また、gcc はリンク時に、通常のＣプログラムを起動・終了するための部品やライブラリも手配します。自分の main だけが実行ファイルの全体ではない、という点も重要です。

今回は自作言語に関数を追加しません。Ｃの呼び出し側は既存のコンパイラに任せ、単純な返り値だけを持つアセンブリの関数と結びます。リンクを行う時点では関数を実行せず、１４という返り値を計算して接続先を選ぶこともありません。

３ハンズオン

準備：今回のファイルへ移動する

第１章と同じリナックスのコンテナ内で実行します。まだ入っていなければ、マック側のリポジトリで make -f docker.mk shell を実行してください。その後、コンテナ内で次を実行します。

cd /workspace/textbook/new/labs/ch06

用意したファイルは main.c、answer.h、answer.s、交換用の answer42.s です。最後のファイルは、同じ名前の関数が４２を返す実装です。マック側から編集するときは、リポジトリ内の同じファイルを開きます。

実験１：相手を渡さずに、呼び出し側を作れるか

実行前に：次の１行は answer.s を指定していません。成功するでしょうか。-c がどの工程で止める指定かを根拠に予想します。

gcc -std=c11 -Wall -Wextra -O0 -c main.c -o /tmp/ch06-main.o
echo $?
gcc -c answer.s -o /tmp/ch06-answer.o
nm /tmp/ch06-main.o /tmp/ch06-answer.o

１行目は呼び出す側、３行目は呼ばれる側を、それぞれオブジェクトにします。-O0 は最適化を抑えて観察しやすくする指定です。２行目は直前の処理の終了状態を表示します。nm はオブジェクトなどのシンボルを表示する道具です。実行ファイルのように中の関数を動かす道具ではありません。

実行後に開く：未定義でも、部品は作れる

１行目は成功し、終了状態は０です。nm の主要な表示は次のようになります。表示の空白などは環境によって異なります。

/tmp/ch06-main.o:
                 U answer
0000000000000000 T main

/tmp/ch06-answer.o:
0000000000000000 T answer

U はそのファイル内で未定義、T はコードの領域で定義された外部向けのシンボルを表します。両方に０があっても同じ実行時アドレスという意味ではありません。この段階の値は、それぞれの部品のコード領域内の位置です。

実験２：二つをリンクして動かす

gcc /tmp/ch06-main.o /tmp/ch06-answer.o -o /tmp/ch06-program
/tmp/ch06-program
echo $?

１行目は、作成済みのオブジェクトをリンクします。Ｃのソースをコンパイルし直しているのではありません。リンク成功を確認してから２行目で起動し、３行目で終了状態を表示します。

実行後に開く：返り値が渡る経路

１４が表示されます。起動用のコードが main を呼び、main が answer を呼び、answer の１４が main の返り値になります。その後、終了処理を経て終了状態としてシェルに渡ります。表示したのは最後の echo であり、answer に表示処理はありません。

実験３：再配置の前後を見る

objdump -dr -Mintel /tmp/ch06-main.o
objdump -d -Mintel --disassemble=main /tmp/ch06-program

objdump はファイルの中身を調べる道具です。-d は機械語を命令表記へ戻して表示する逆アセンブル、-r は再配置情報の表示、-Mintel は命令の表示を本書と同じ記法にする指定です。２行目は、リンク後の main の命令だけに表示を絞っています。

観察する場所：１行目の出力から call と、その近くの answer を探します。次に２行目の call の行と比較します。ほかの命令を全部解読する必要はありません。

観察後に開く：命令に付随した調整情報

検証環境では、リンク前に次の表示がありました。

8: e8 00 00 00 00   call d <main+0xd>
       9: R_X86_64_PLT32 answer-0x4

e8 はこの call の命令コードで、続く４バイトが距離の欄です。この時点では０が置かれています。下の行は、９という位置の欄を answer に基づいて調整する再配置情報です。R_X86_64_PLT32 は調整方式の名前、-0x4 は距離を求める基準を合わせるための補正で、answer の返り値から４を引く指示ではありません。

リンク後は、検証環境で次のようになりました。

1131: e8 02 00 00 00   call 1138 <answer>

この数値は１６進表記です。call の次の命令は 1136、answer は 1138 なので、距離の欄に２が入っています。アドレスや周囲の命令は環境で変わります。数字の一致ではなく、リンク前の調整情報と、リンク後に answer を指す call の対応を確認してください。

実験４：呼ぶ側を作り直さず、返す値を変える

今度は４２を返す部品に交換します。main.c はコンパイルし直しません。実験１で作った main.o をそのまま使えるか、予想します。

gcc -c answer42.s -o /tmp/ch06-answer42.o
gcc /tmp/ch06-main.o /tmp/ch06-answer42.o -o /tmp/ch06-program42
/tmp/ch06-program42
echo $?
実行後に開く：接続する名前は同じ

結果は４２です。ファイル名は answer42.s ですが、中のシンボル名は answer のままです。main.o は「answer を呼びたい」という情報を持つため、新しい定義にもつながります。関数名と型などの取り決めを変えず本体だけを変えたので、呼び出し側を作り直す必要がありませんでした。ただし、新しい部品を使うための再リンクは必要です。

以前の /tmp/ch06-program を動かすと、今でも１４を返します。新しいファイルを作っただけで、すでにリンク済みの古い実行ファイルが書き換わることはありません。

実験５：部品を省く、二つとも渡す

次は、意図的に失敗させる実験です。最初は定義を一つも渡さず、その後は二つ渡します。それぞれ、コンパイル・リンク・実行のどの段階で止まるか予想してください。

gcc /tmp/ch06-main.o -o /tmp/ch06-missing
echo $?

gcc /tmp/ch06-main.o /tmp/ch06-answer.o /tmp/ch06-answer42.o -o /tmp/ch06-duplicate
echo $?

エラーメッセージの中の answer を探してください。失敗したコマンドの直後の echo $? は、リンクを手配した gcc の終了状態を表示します。生成プログラムの終了状態ではありません。ここでは失敗するので、出力先を起動する手順はありません。

実行後に開く：未定義と重複

最初は answer への undefined reference、次は answer の multiple definition が出て、どちらも終了状態は０以外になります。最初の失敗はヘッダ不足ではありません。宣言を読んで main.o を作る工程は成功しており、リンクに渡した本体が不足しています。二つ目は、どちらも同じ名前を定義する部品を直接渡したことが原因です。

全体を確認する 検証スクリプトも用意しています。第６章のフォルダで bash check.sh を実行すると、結果、シンボル、再配置情報、想定した二つのリンクエラーを確認します。教材ファイルを変更した場合は、元の内容に戻してから実行してください。

４理解チェック

answer.h を読んだのに、main.o だけではリンクできないのはなぜか？

解説を読む

ヘッダには名前と型の宣言があるだけで、関数本体がないからです。宣言は呼び出し側のコンパイルに、本体の定義はリンクで参照先を結び付けるために必要です。

nm の U answer は、その時点でビルド失敗を意味するか？

解説を読む

いいえ。そのオブジェクト内に定義がないことを示すだけです。後で別の部品の定義へつなぐための正常な中間状態でもあります。今回、適切な定義を渡さず実行ファイルを作ろうとするとリンクが失敗します。

シンボル解決と再配置は、何が違うか？

解説を読む

シンボル解決は「この参照をどの定義につなぐか」を決める仕事です。再配置は、その位置に合わせて参照箇所の数値を調整する仕事です。本章では、answer の定義を見つけ、その位置へ届くよう call の距離を調整しました。

answer42.o を作ったのに、古い実行ファイルが１４を返すのはなぜか？

解説を読む

新しいオブジェクトを作る処理と、実行ファイルへ組み込むリンクは別だからです。本章の古い実行ファイルには、すでに１４を返す本体が組み込まれています。新しいオブジェクトを使って再リンクし、その新しい実行ファイルを起動する必要があります。

answer.s から .globl answer を外すと、名前が消えるのか？

解説を読む

answer: があるため名前そのものは残りますが、外部から参照できる定義ではなくなります。通常、nm では小文字の t として見えます。別のオブジェクトの main が求める外部向けの answer を満たせないため、今回のリンクは失敗します。

リンクできれば、Ｃの宣言とアセンブリの実装の型も正しいか？

解説を読む

保証されません。今回の通常のリンクでは、関数の型の整合性をＣコンパイラのように検査するわけではありません。名前の接続と、実行時に値を正しく受け渡せることは別の条件です。
