第５章

式のコード生成

木が表す計算の順序を、ＣＰＵが実行する命令の並びに変える。

前章では式の構造が見えるようになりました。今回は、その木を使ってアセンブリを出力します。第２章では数一つしか扱えなかったコンパイラが、括弧を含む四則演算を扱えるようになります。

１この章で扱う問い

式の構造から、途中結果を失わずに計算する命令をどう作るか？

2+3*4 の木は、足し算の右の子に掛け算を持っています。最後に足すには、２と、３×４の結果の両方が必要です。しかし、どちらの計算にも rax を使うと、右側の計算中に左側の値が上書きされます。「どの演算を先にするか」だけでなく、「待っている結果をどこに置くか」も決めなければなりません。

前提は、第１章のレジスタと ret、第２章のコンパイルから実行までの流れ、第４章の構文木です。スタックへの値の保存と取り出しは、この章で説明します。

２この章の理論

構造を決める工程と、命令を作る工程を分ける

コード生成は、構文木などの情報を使って、目的の計算を実行するコードを作る工程です。本章では、出力先のコードを x86-64 のアセンブリにします。字句解析と構文解析は前章の実装を引き継ぎ、木を表示していた部分を、命令を出力する処理に置き換えます。

どの部分木も「結果を rax に残す」と決める

木の一つのノードと、その下につながる部分を部分木と呼びます。数一つも部分木です。コード生成では、どの部分木にも同じ約束を設けると、内側の細かい構造を知らなくても結果を組み合わせられます。

本章の約束は、その部分木の命令を実行し終えると、結果が rax に入り、一時保存のために使ったスタックは開始時の状態に戻ることです。たとえば右の子が数３でも、複雑な掛け算でも、最後には rax を読めば結果がわかります。

数の葉なら mov rax, 数 を出せば、この約束を満たせます。演算ノードなら、左の子の命令、右の子の命令、両者を組み合わせる命令が必要です。ただし、その間に左の結果を保管する場所が要ります。

スタックは、後で使う値を重ねて保存する場所

スタックは、最後に保存した値から取り出す使い方をするメモリ領域です。今回の push rax は rax の値をスタックに保存し、pop rax は最後に保存した値を rax に取り出します。push をしても、元の rax の値は消えません。

保存位置を管理するレジスタが rsp です。今回の６４ビットの push は rsp を８バイト分小さくし、その位置に値を置きます。pop はその位置の値を読み、rsp を８バイト分大きくして戻します。取り出した場所のメモリを０に消すのではなく、次に使う位置を戻しています。

「戻り先」は、main が呼ばれたときに保存された戻りアドレスです。式のために保存した値をすべて取り出してから ret に進めば、ret は元の戻りアドレスを使えます。保存した値を残したままだと、それを戻りアドレスとして扱ってしまうため、push と pop の対応は計算結果だけでなく正常に戻るためにも必要です。

左を保存し、右を計算してから組み合わせる

演算ノードでは、次の順に命令を出します。rdi は、左右の結果がそろった最後の段階で、右の値を一時的に置くレジスタとして使います。

  1. 左の部分木の命令を出す。実行後、左の結果が rax に入る。
  2. push rax を出す。左の結果を保存する。
  3. 右の部分木の命令を出す。実行後、右の結果が rax に入る。
  4. mov rdi, rax を出す。右の結果を rdi に移す。
  5. pop rax を出す。保存していた左の結果を rax に戻す。
  6. 演算の命令を出す。左右を組み合わせた結果を rax に残す。

右の部分木も同じ約束を守るため、右の計算が終わったときには、左の値がスタックの先頭に残っています。これを取り出せば、親の演算も約束を守れます。最初から左の値を rdi に置いて待つだけでは、右の部分木も rdi を使うため上書きされてしまいます。

四則演算を命令に対応させる

次の表は、rax に左の結果、rdi に右の結果がそろった後の処理です。

演算出力する命令実行すると何が起きるか
＋add rax, rdi左右の和を rax に入れる。
－sub rax, rdi左から右を引いた値を rax に入れる。
＊imul rax, rdi左右の積を rax に入れる。
／cqo の後に idiv rdi左を右で割り、整数の商を rax に入れる。

割り算だけ準備があるのは、idiv rdi が、割られる値を rax 一つではなく、rdx を上位、rax を下位とする１２８ビットの組で読むためです。cqo は rax の符号を保ったままその幅へ広げる命令です。正または０なら rdx をすべて０、負ならすべて１にします。rax 自体の値は変えません。

idiv の後、商は rax、余りは rdx に入ります。本章では余りを使いません。整数の割り算なので 8/3 は２です。負の商も０に近づく方向へ端数を捨てるため、(0-9)/2 は－４になります。引き算と割り算は、左右を逆にすると結果が変わる点にも注意してください。

生成処理の実装を読む

完成した実装は compiler.c です。前章の字句解析・構文解析を残し、木の表示関数の代わりに次の関数を用意しています。node->op が '\0' なら数、それ以外なら演算ノードでした。

static void generate(const Node *node) {
    if (node->op == '\0') {
        printf("    mov rax, %d\n", node->value);
        return;
    }
    generate(node->left);
    printf("    push rax\n");
    generate(node->right);
    printf("    mov rdi, rax\n");
    printf("    pop rax\n");
    switch (node->op) {
        case '+': printf("    add rax, rdi\n"); break;
        case '-': printf("    sub rax, rdi\n"); break;
        case '*': printf("    imul rax, rdi\n"); break;
        case '/':
            printf("    cqo\n");
            printf("    idiv rdi\n");
            break;
    }
}

generate(node->left) は、左の子に対応する命令をすべて出力してから戻ります。右の子も同様です。ここで再帰的に呼ばれているのは、コンパイラ内のＣの関数です。生成されるプログラムには、この再帰呼び出しに対応する call はなく、計算命令が順に並びます。

構文解析に成功したら、main: などの見出しを出力し、generate(root) で式全体の命令を出し、最後に ret を出します。根の処理も「結果は rax」という約束を守るので、その値を返せます。優先順位を生成側で判定し直す必要はありません。括弧や優先順位は、すでに木の親子関係になっています。

今回扱う範囲

入力中の数は前章と同じ０〜２５５、入力長は１０２４バイトまでです。＋、－、＊、／と括弧を扱い、単独の負号はまだ扱いません。ただし 3-5 のように計算結果が負になる式は扱います。計算には６４ビットのレジスタを使いますが、ゼロ除算や、その計算範囲を超える場合の診断は実装していません。

生成に成功したことと、生成されたプログラムが安全に実行できることは別です。たとえば 3/0 は文法に合うので命令を生成しますが、実行するとゼロ除算になります。本章の実験では使いません。また、シェルの終了状態で観察できるのは０〜２５５です。計算結果全体を表示する仕組みではありません。

３ハンズオン

準備：コンパイラ自身を作る

第１章と同じコンテナ内で実行します。まだ入っていなければ、マック側でリポジトリのフォルダへ移動し、make -f docker.mk shell を実行してください。次の２行はコンテナ内で実行します。

cd /workspace/textbook/new/labs/ch05
gcc -std=c11 -Wall -Wextra -o /tmp/ch05-compiler compiler.c

cd は実験フォルダへの移動です。gcc はＣで書いたコンパイラを実行ファイルにします。-std=c11 はＣの規格、-Wall -Wextra は警告の指定、-o の後は保存先です。エラーが出ずに完了したことを確認します。

編集するときは、マック側のエディタで textbook/new/labs/ch05/compiler.c を開けます。コンテナの /workspace は、このリポジトリを共有している場所です。マック側の nvim で編集して保存した内容も、コンテナから読めます。

実験１：木から出た命令と、実行結果をつなぐ

実行前に：2+3*4 の根の演算は何でしょうか。最後に出る計算命令と、完成したプログラムの結果を予想してください。

/tmp/ch05-compiler '2+3*4' > /tmp/ch05-result.s
echo $?
cat /tmp/ch05-result.s

１行目は自作コンパイラを動かし、出力をファイルへ保存します。引用符は、＊などをシェルに特別扱いさせず、式を一つの引数として渡すために付けています。２行目の $? は直前のコンパイラの終了状態で、echo がそれを表示します。３行目の cat は保存した文字列を表示します。

ここで出る終了状態は０です。まだ１４を計算するプログラムは実行していません。表示された命令を図３と照合し、次へ進みます。

gcc -o /tmp/ch05-program /tmp/ch05-result.s
/tmp/ch05-program
echo $?

１行目は、アセンブリのファイルをアセンブル・リンクして実行ファイルにします。入力が .s なので、Ｃからアセンブリに変換する工程は不要です。ビルド成功後、２行目で生成されたプログラムを起動し、３行目でその終了状態を表示します。

実行後に開く：２種類の終了状態

コンパイラの終了状態は０、生成されたプログラムの終了状態は１４です。前者は変換処理の成功、後者は今回の式の結果に対応しています。生成されたプログラム自身に表示処理はないため、２行目だけでは１４は画面に出ません。

実験２：括弧で、命令の順序はどう変わるか

入力だけを (2+3)*4 に変えます。今度はどの計算命令が先に出るか予想してから、生成・表示・ビルド・実行をやり直してください。

/tmp/ch05-compiler '(2+3)*4' > /tmp/ch05-result.s
cat /tmp/ch05-result.s
gcc -o /tmp/ch05-program /tmp/ch05-result.s
/tmp/ch05-program
echo $?
実行後に開く：木の形が命令に残る

add が先、imul が後になり、結果は２０です。前の実験では imul が先でした。生成関数は括弧の文字を見ていません。構文解析が作った木の形に従ったことで、順序が変わります。

同じ手順で 9-3-2 と 9-(3-2)、さらに 8/3 も試してください。入力を変えたら、アセンブリの生成と実行ファイルのビルドの両方をやり直します。どちらかを省くと、以前のプログラムを実行することになります。

結果を照合する

順に４、８、２です。前の二つは木の結合の違い、最後は整数の割り算であることを確認する実験です。

実験３：内側の計算が、外側の保存値を守るか

(2+3)*(4+5) の命令を生成して表示します。まだ実行せず、各 push で何を保存し、どの pop がそれを取り出すかをメモしてください。図３と同じ形式で、右の足し算を計算している間の保存値を追います。

予想ができたら、実験２の手順でビルド・実行します。終了状態は最終結果だけを示すので、途中の保存状態そのものを観測したわけではありません。生成された命令を読んだ予測と、最終結果が整合するかを確かめる実験です。

実行後に開く：５を残したまま、４＋５を計算する

左の足し算で２を保存し、３を計算した後に２を取り出して５を作ります。その５を掛け算の左の結果として保存します。右の足し算ではさらに４を保存し、右端の５を計算して４を取り出します。右側が９になった時点でも、外側が保存した５は残っています。最後にその５を取り出し、９と掛けて４５になります。

実験４：生成規則を一つ変え、影響を確かめる

compiler.c の generate 内で、case '-' が出力する sub rax, rdi だけを add rax, rdi に変えます。字句解析や構文解析は変えません。8-3 の結果がどうなるか予想してください。

準備の gcc でコンパイラ自身を作り直し、次に 8-3 のアセンブリを生成し、それをビルド・実行します。表示されたアセンブリも確認してください。

実行後に開く：構文木は正しくても、生成が違えば結果が変わる

引き算の木に対して足し算の命令を出すため、結果は１１になります。入力を正しく構造化する仕事と、その構造に合う命令を選ぶ仕事は別です。コンパイラだけを作り直しても、以前に生成した実行ファイルは変わりません。

実験後は sub に戻し、コンパイラをビルドし直してください。戻した状態で bash check.sh を実行すると、用意した複数の式について、生成から実行までをまとめて確認できます。

４理解チェック

右側の計算が複雑でも、親の演算が組み合わせられるのはなぜか？

解説を読む

各部分木が、結果を rax に残し、スタックを開始時の状態に戻す約束を守るからです。親は右側の内部構造を知らなくても、保存した左の値と rax の右の値を使えます。

左の値を最初から rdi に置いて、右側を計算してはいけないのか？

解説を読む

今回の生成方法では、右側の演算も rdi を使います。右側が数一つなら動く場合がありますが、入れ子の演算では左の値が上書きされます。スタックなら、内側の処理が自分の保存値だけを取り出すことで外側の値を守れます。

pop rax の前に mov rdi, rax を出すのはなぜか？

解説を読む

その時点の rax には右の結果があります。先に左の値を pop rax すると、右の結果を失います。右を rdi に移してから左を戻すことで、左右の値が同時にそろいます。

push の値を一つ残したまま ret へ進むと、何が困るか？

解説を読む

スタックの先頭が元の戻りアドレスではなく一時保存値になっています。ret はそれを戻り先として取り出すため、正しい場所へ戻れません。計算値が正しくても、保存と取り出しの対応が崩れていればプログラムは正しく動きません。

200+100 の終了状態が４４でも、足し算を間違えたとは限らないのはなぜか？

解説を読む

レジスタ上の計算結果は３００ですが、この環境でシェルへ伝わる終了状態は下位８ビットです。３００を２５６で割った余りの４４になります。終了状態だけでは、元の計算結果の全体はわかりません。負の値もそのまま表示されるわけではなく、3-5 なら２５４になります。

コンパイラの終了状態が０なら、ゼロ除算も検査済みか？

解説を読む

いいえ。今回の０は、入力を解析して命令を出力できたことを示します。ゼロ除算を事前に調べる処理はありません。命令生成の成功と、生成されたプログラムの実行時の振る舞いを分けて考えます。
