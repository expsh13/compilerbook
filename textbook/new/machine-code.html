第１章

機械語とアセンブラ

一つの命令が、値をどう変えるか。その積み重ねから、プログラムの動きを理解する。

これから作るコンパイラは、まずアセンブリ言語を出力するものにします。その出力が何を意味するのかを知るため、この章では自分で短いアセンブリコードを読み、変更し、実行結果を確かめます。

１この章で扱う問い

コンパイラが出力するコードは、どう実行され、計算結果を生むのか？

この問いを、「命令がどこにあり、何を変え、結果をどう受け渡すか」に分けて考えます。最後には、短い命令列から結果を予想し、命令を一つ変更すると結果が変わる理由を説明できることを目指します。

対象は、リポジトリの開発環境と同じ、リナックス上の６４ビットのエックス８６系ＣＰＵです。アセンブリの命令や関数の呼び出し方は、ＣＰＵや基本ソフトによって異なります。ここで確かめた具体的な書き方を、すべてのコンピュータにそのまま適用することはできません。

２この章の理論

命令は「状態をどう変えるか」を指定する

計算の途中の値を保持する場所がなければ、次の計算にその値を使えません。ＣＰＵ内部には、値を保持する小さな記憶場所であるレジスタがあります。本章では、そのうちの rax と rcx を使います。どちらも６４ビットの値を保持できます。

ＣＰＵは、メモリ上に置かれた命令を読み、その命令で指定された操作を行います。操作の結果として、レジスタやメモリの内容、次に実行する命令の位置などが変化します。この「ある時点で何がどの値になっているか」を、ここでは状態と呼びます。

メモリには場所を識別する番号であるアドレスがあり、命令もデータもバイト列として置かれます。１バイトは８ビットです。命令の位置を扱う rip というレジスタもありますが、今回は自分で操作しません。分岐のない今回の計算部分は、上から順に命令をたどれば理解できます。実際のＣＰＵ内部の並列処理やキャッシュは、この章では扱いません。

今回区別したい３つのもの
対象役割混同しないこと
レジスタＣＰＵ内部で値を保持する。rax は記憶場所の名前であり、その時点の値そのものではない。
メモリ命令やデータを置く。アドレスは場所、その場所のバイト列は中身。
命令値のコピーや加算などの操作を指定する。命令を表す文字列と、ＣＰＵが読む機械語は別の表現。

アセンブリ言語と機械語の関係

mov rax, 7 は、人間が読める形で命令を記述したアセンブリ言語です。ＣＰＵがこの文字列を直接読んでいるわけではありません。アセンブラというプログラムが、命令の規則に従って機械語のバイト列に変換します。

本書でまず作るコンパイラは、このアセンブリ言語までを出力します。その後、既存の道具で機械語への変換と、実行に必要な部品の結合を行います。後者をリンクと呼びます。コンパイラが直接機械語を作る設計もありますが、本書では工程を分けることで、生成した命令を目で確認できます。

  1. ソースコードから、コンパイラがアセンブリコードを生成する。
  2. アセンブラが機械語を含むオブジェクトファイルを作る。
  3. リンカが必要な部品を結合し、実行ファイルを作る。
  4. 起動の仕組みが実行の準備を整え、ＣＰＵが命令を実行する。

この章では、１の出力に相当するコードを手で用意します。実行ファイルには自分の命令以外の情報や起動用のコードも含まれます。「アセンブリの文字列を、そのまま実行可能なファイルに保存しただけ」ではない点を押さえてください。

３つの命令で値の変化を読む

ここではインテル形式という記法を使います。以下の命令では、左側が書き換える対象、右側が使う値です。数値を直接書いた 7 のような値は即値と呼びます。

命令実行すること
mov rax, 7rax の値を７にする。それ以前の値は上書きされる。
add rax, 5現在の rax の値に５を加え、その結果を rax に入れる。
sub rax, 3現在の rax の値から３を引き、その結果を rax に入れる。

mov rcx, rax と書けば、その瞬間の rax の値を rcx にコピーします。２つのレジスタが同じ記憶場所になるわけではありません。その後で rax を変えても、コピー済みの rcx は自動では変わりません。

なお、加減算は条件判定に使うフラグも変更します。この章の命令列はフラグを利用しないため、観察する状態をレジスタの値に絞っています。

結果を計算することと、結果を返すこと

関数の呼び出し元が結果を受け取るには、結果をどこに置くかの取り決めが必要です。今回の環境では、整数を返す関数は rax 系のレジスタを使います。ここで、６４ビット全体を指す rax と、その一部分を指す eax の関係を押さえます。

eax は、rax の下位３２ビットを指す名前です。別々の記憶場所ではありません。２進数を通常のように左から上位の桁、右へ下位の桁と並べると、右側の３２桁が eax に当たります。

今回の環境のＣの int は３２ビットです。そのため、int を返す main の呼び出し元は、eax の部分を返り値として読みます。rax から別の場所へコピーして受け取る、という意味ではありません。

たとえば mov rax, 9 で９を入れると、上位３２ビットはすべて０になり、下位３２ビットが９を表します。全体を読んでも、eax の部分だけを読んでも値は９です。本章で扱う小さな正の整数では、このように読む幅の違いが値の違いにならないため、rax に置いた値をそのまま返り値として考えられます。

値を用意してから呼び出し元へ戻るところを、短い例で見てみます。次は、９を返す main の本体部分です。実行ファイルを作るための指定は省略しています。

main:
    mov rax, 9
    ret

main: は、この関数の開始位置に付けた名前です。そこから実行が始まると、mov rax, 9 が返す値の９を用意し、続く ret が呼び出し元へ実行を戻します。

ret は、今の関数の実行を終え、呼び出した側の「続き」へ戻る命令です。関数を呼び出す call 命令を実行すると、ＣＰＵは「呼び出しが終わったら再開する場所」を保存してから、呼び出す関数へ実行を移します。この保存された場所を戻りアドレスと呼びます。ret はそのアドレスを取り出し、そこから命令の実行を再開します。

戻りアドレスは、メモリ上のスタックという領域に保存されます。スタックの詳しい仕組みは後の章で扱います。ここでは、呼び出すときに戻り先を保存するので、関数側は呼び出し元の場所を固定して書かなくても戻れる、と押さえてください。

今回の例では、次の順序で処理が進みます。

  1. 起動用のコードが main を呼び出す。その際、呼び出し命令の次の位置が戻りアドレスとして保存される。
  2. main の mov rax, 9 が、返す値の９を用意する。
  3. ret が保存された戻りアドレスを使い、起動用のコードの続きへ実行を戻す。
  4. 起動用のコードが返り値の９を受け取り、プログラムの終了処理を進める。

mov が「返す値」を用意し、ret が「実行する場所」を戻します。返り値と戻りアドレスは別のものです。この例では返り値は９ですが、戻りアドレスは起動用のコードの続きを指す場所です。

終了処理を経て、返した値がプログラムの終了状態として伝わります。シェルの $? は直前のコマンドの終了状態です。通常、０は成功、０以外は失敗などを表すために使いますが、この実験では計算結果を見る窓として利用します。

終了状態で観察できる値は０から２５５までです。大きな整数の結果をすべて観察できるわけではありません。また、最終結果だけでは途中の状態までは確定しません。同じ結果になる異なる命令列もあります。

３ハンズオン

短い命令列について、紙やメモ上で値の変化を予想し、実行結果と照合します。その後、一つの命令を変え、さらにレジスタ間のコピーを試します。最後に、書いた命令が機械語のバイト列になっていることを確認します。

準備：実行する環境をそろえる

このリポジトリには、対象のリナックス環境を用意する Dockerfile と docker.mk があります。マック本体のコンパイラでは環境が異なるため、以下ではコンテナ内の gcc と objdump を使います。まず、利用中のコンテナ実行アプリを起動してください。

マック側のターミナルで、リポジトリのルートから次を実行します。初回のイメージ作成にはネットワーク接続が必要です。すでにイメージを作成済みなら、最初のビルドは省略できます。

cd /Users/hatasatoki/Develops/compilerbook
make -f docker.mk image
make -f docker.mk shell

image は道具を含む環境を作り、shell はその環境内のシェルを開きます。リポジトリはコンテナ内の /workspace で参照できます。以下のコマンドは、特記がない限りこのコンテナ内で実行します。

uname -m
cd /workspace/textbook/new/labs/ch01

uname -m が x86_64 と表示されることを確認します。接続エラーが出る場合はコンテナ実行アプリの起動状態を確認してください。命令を受け付けない場合は、マック側のターミナルで実行していないか、対象の環境で動いているかを確かめます。

実験１：計算結果を予想して実行する

用意した計算用ファイルは次の内容です。マック側のエディタで同じファイルを開いて編集できます。命令以外の行にも役割があるため、まず全体を見てください。

.intel_syntax noprefix
.text
.globl main
main:
    mov rax, 7
    add rax, 5
    sub rax, 3
    ret
.section .note.GNU-stack,"",@progbits

.intel_syntax noprefix はアセンブラへの記法の指定です。.text は命令を置く領域を選び、.globl main は main を別の部品から参照できる名前にします。main: はその位置に付けたラベルです。これらはＣＰＵが順番に実行する計算命令ではありません。

最後の .note.GNU-stack の指定は、実行可能なスタックを必要としないことをツールに伝えるための情報です。今は計算には関与しない付帯情報として扱い、残してください。

実行する前に：３つの計算命令の直後に、rax がそれぞれいくつになるか書いてください。初期値は０だと仮定せず、最初の命令で何が確定するかを考えます。

gcc -o /tmp/compilerbook-ch01-arithmetic arithmetic.s
/tmp/compilerbook-ch01-arithmetic
echo $?

gcc はここでは道具の呼び出し役です。拡張子が .s なのでアセンブラに渡し、その後リンクして、-o で指定した実行ファイルを作ります。生成に成功したことを確認してから実行してください。失敗したのに実行すると、以前作ったファイルの結果を見てしまうことがあります。

echo $? はプログラムの直後に実行します。間に別のコマンドを挟むと、そのコマンドの終了状態へ変わります。実行ファイル自身は文字を出力しないため、何も表示されずに終了しても正常です。

実行後に開く：結果と途中状態

終了状態は９です。最初の命令で７が入り、次に１２、次に９になります。最後に ret で呼び出し元へ戻ります。

実行済みの命令直後の値
mov rax, 7７
add rax, 5１２
sub rax, 3９

この表は命令の意味から導いた途中状態です。今回、実行によって直接観察したのは最後の終了状態です。この２つは区別しておきます。

実験２：加算を、上書きに変える

arithmetic.s の add rax, 5 だけを mov rax, 5 に変更します。結果を予想してから、実験１の３つのコマンドを再実行してください。編集後は必ず再ビルドします。ソースを保存しただけでは、前の実行ファイルは変わりません。

変更後に開く：どの情報が失われたか

結果は２です。７を入れた後に５で上書きし、その５から３を引きます。加算と異なり、２番目の命令は以前の値を使いません。この命令列では最初の７を別の値に変えても、２番目の命令で５に上書きされるため、最終結果は変わりません。

ここまで読んだら、最初の７を１０に変えて再ビルドし、本当に同じ結果になるか試してください。「どこまでの変更が結果に影響するか」も、命令列から読み取れます。実験後は元の７と add に戻しておきます。

実験３：コピーした値は、元の値に追従するか

次はコピー用ファイルを使います。指定やラベルは実験１と同じで、計算部分が次のようになっています。

    mov rax, 7
    mov rcx, rax
    add rax, 5
    sub rcx, 3
    mov rax, rcx
    ret

２列のメモを作り、各命令の直後の rax と rcx を追ってください。まだ値を設定していない場所は「未設定」と書きます。特に、３番目の命令で rcx も変わるかどうかを予想してから実行します。

gcc -o /tmp/compilerbook-ch01-copy copy.s
/tmp/compilerbook-ch01-copy
echo $?
実行後に開く：２つの値を分けて追う

結果は４です。コピー直後は両方７ですが、加算後は rax だけ１２になります。rcx は７のままなので、そこから３を引いて４になります。最後にその４を rax へコピーして返します。

最後の mov rax, rcx を除くと、返す値は１２になります。rcx に計算結果があっても、呼び出し元が結果を読む場所に置かなければ、その値は返りません。予想をメモしてから、その一行を外して再ビルドし、確かめてください。

実験４：書いた命令と機械語を対応させる

元に戻した arithmetic.s から、リンク前のオブジェクトファイルを作ります。-c はリンク前で止める指定です。今回は自分の命令だけを見やすくするため、この段階で観察します。

gcc -c -o /tmp/compilerbook-ch01-arithmetic.o arithmetic.s
objdump -d -M intel /tmp/compilerbook-ch01-arithmetic.o

objdump はファイルの内容を調べる道具です。-d は機械語から読みやすい命令表記を得る逆アセンブル、-M intel は表示形式の指定です。結果の <main>: 以下に、位置、機械語のバイト列、命令が並びます。

中央の２桁ずつの１６進数は、それぞれ１バイトを表します。右側の命令と対応させ、mov、add、sub、ret を探してください。即値の７が 0x7 のように表示されても、表記が違うだけで同じ値です。

観察すること：各命令は何バイトあるでしょうか。隣の命令の位置との差と一致するでしょうか。ここに表示される位置は、リンク前の命令領域内での相対的な位置であり、実行時の最終的なアドレスではありません。

観察後に開く：１行と１バイトは同じではない

今回の環境の一般的な出力では、最初の命令は 48 c7 c0 07 00 00 00 の７バイト、続く加算と減算は各４バイト、ret は c3 の１バイトです。命令の開始位置は１６進数で 0、7、b、f となります。

機械語の命令の長さは一定ではありません。ＣＰＵは改行を探して命令を区切るのではなく、命令の形式に従って読み解きます。また、同じ操作を表す符号化が複数ある場合もあるため、道具が変わると同じ意味でもバイト列が変わることがあります。

実験５：スタック上の戻りアドレスを見る

今度は、実行を途中で止めて、メモリに保存されている戻りアドレスを直接見ます。その後、ret を１命令だけ実行し、保存されていた場所へ本当に戻ったかを確かめます。実行を止めたり、メモリを調べたりする道具をデバッガと呼びます。ここでは、教材のコンテナに入っている gdb を使います。

この実験は、arithmetic.s の計算部分を元の mov rax, 7、add rax, 5、sub rax, 3、ret の４命令に戻してから行います。命令の追加や並べ替えをしていると、以下の「３命令進める」で止まる場所が変わります。

① デバッガを起動し、関数の入り口で止める

今回のマックとコンテナの組み合わせでは、ＧＤＢから直接起動すると、変換実行中のレジスタを取得できませんでした。そこで、ＱＥＭＵが教材プログラムを実行し、ＧＤＢはＱＥＭＵのデバッグ窓口へ接続する方法を使います。以下は、この環境で関数の入り口への停止とスタックの読み取りまで確認できた手順です。

まず、コンテナ内に追加の道具を入れます。インストールが成功して、バージョンが表示されてから先へ進んでください。

sudo apt-get update
sudo apt-get install -y qemu-user
qemu-x86_64 --version

今回の環境では qemu-user を使い、実行コマンドは qemu-x86_64 です。古い案内にある qemu-user-static と qemu-x86_64-static は、この環境では使いません。コンテナを削除して作り直した場合、追加インストールもやり直す必要があります。

まず、コンテナ内のシェルで次を実行します。-g はデバッグ用の情報を付ける指定、-no-pie は今回の観察で実行ファイルのコードの位置を扱いやすくする指定です。スタックや共有ライブラリのアドレスまで固定するものではありません。

cd /workspace/textbook/new/labs/ch01
gcc -g -no-pie -o /tmp/compilerbook-ch01-stack arithmetic.s
qemu-x86_64 -g 1234 /tmp/compilerbook-ch01-stack &
gdb -q /tmp/compilerbook-ch01-stack

ＱＥＭＵの -g 1234 は、１２３４番のポートでデバッガの接続を待つ指定です。末尾の & はバックグラウンドで動かし、同じターミナルから次のコマンドを入力できるようにします。ここでの -g は、先ほどの gcc のデバッグ情報の指定とは別の意味です。

(gdb) と表示されたら、以降はシェルではなくデバッガに指示を出しています。次の行を順番に入力してください。(gdb) という文字自体は入力しません。

set disassembly-flavor intel
target remote localhost:1234
break *main
continue
x/i $rip

最初の行は命令表示を教材と同じインテル形式にそろえます。２行目は同じコンテナ内のＱＥＭＵへ接続します。接続直後は、main より前の起動処理で止まっていることがあります。break *main で main の最初の命令の位置に停止地点を置き、continue でそこまで進めます。今回はすでにＱＥＭＵがプログラムを起動しているので、run は使いません。

接続時にファイル転送が遅いという警告や、ライブラリのデバッグ情報がないという表示が出ても、続けて main に停止できれば今回の観察は進められます。

rip は命令の位置を扱うレジスタです。停止中の $rip は、これから実行する命令のアドレスを表します。x/i $rip は、その場所の命令を１つ表示します。ここで mov rax, 0x7 が見えることを確認します。

② スタックに保存されている値を見る

rsp はスタックの先頭のアドレスを保持するレジスタです。この関数に入った直後は、そこに呼び出し元が保存した８バイトの戻りアドレスがあります。rsp の値と、その場所に入っている値を分けて見ます。

info registers rsp rip
x/gx $rsp

info registers は指定したレジスタを表示します。x/gx $rsp は、rsp が指すメモリを８バイト単位で１つ、１６進数で表示します。g が８バイト、後ろの x が１６進数の指定です。

0x7ffffeb894f8:  0x00007ffffe0c9601

上は今回実際に観察した出力です。左側の 0x7ffffeb894f8 は保存している場所で、rsp の値と一致します。右側の 0x00007ffffe0c9601 はそこに保存されている戻りアドレスです。図のＢに相当するのは右側です。実際の数字は環境や実行ごとに変わるので、例と一致させる必要はありません。

コマンドは１行ずつ入力します。x/gx $rsp の後に余分な改行や - が混ざると、式の構文エラーになります。この場合は余分な文字を除き、その１行を入力し直してください。

比較のため、この２つをデバッガ内のメモ用変数に保存します。プログラムのレジスタやメモリを書き換える操作ではありません。

set $saved_rsp = $rsp
set $saved_return = *(unsigned long long *)$rsp
x/i $saved_return

$saved_rsp は現在のスタックの位置、$saved_return はそこから読んだ戻りアドレスです。２行目の式は、この環境で「rsp の場所から８バイトの整数を読む」という意味です。最後の行では、保存された戻り先にある命令を表示します。自分で書いた main の外の命令が見えますが、今はその命令自体の意味を理解する必要はありません。

③ 計算を進めて、戻る直前を観察する

stepi 3
x/i $rip
print /d $rax
x/gx $rsp

stepi 3 は機械語の命令を３つ実行して停止します。元の教材コードなら、次の命令は ret、rax の値は９です。print /d は値を１０進数で表示する指定です。この３つの計算命令はスタックを変更しないため、スタック先頭の戻りアドレスも先ほどと同じです。

進める前に予想：ret の直後、rip はどの値になるでしょうか。８バイトの戻りアドレスを取り出した後、rsp はどう変わるでしょうか。

④ 戻った場所を比較する

x/i $rip が ret を指していることを確認してから、次を入力します。

stepi
print /x $rip
print /x $saved_return
print $rip == $saved_return
print /d $rsp - $saved_rsp
x/i $rip
観察後に開く：保存された場所へ戻ったか

$rip と $saved_return は同じアドレスになります。一致を調べる式は、真を表す１を返します。また、$rsp - $saved_rsp は８です。今回の ret は、スタック先頭の８バイトを戻り先として使い、スタックの先頭を８バイト先へ進めます。

スタックから「取り出す」といっても、元のメモリを０で消すわけではありません。先頭を示す rsp が動き、取り出した場所が現在のスタックの範囲から外れます。ここでは、戻りアドレスが積まれた後の状態と、取り出す前後を観察しました。call が保存する瞬間そのものは、まだ観察していません。

確認できたら、continue で終了まで進め、quit でデバッガを閉じます。デバッガを終了した後のシェルの $? はデバッガ自身の終了状態なので、教材プログラムの結果と混同しないでください。

continue
quit
デバッガで停止できない場合

Cannot PTRACE_GETREGS や Couldn't get registers が出た場合は、以前の直接起動の手順を使っていないか確認します。今回の環境では、その方法は失敗し、ＱＥＭＵへ target remote で接続する方法で観察できました。直接起動中のＧＤＢは quit で終了し、確認が出たら応答してから、①の接続手順に進みます。

マック上で別のＣＰＵ向けのコンテナを動かしている場合、変換実行の仕組みがデバッグ操作に対応していないことがあります。また、コンテナの権限設定でプロセスの観察が制限される場合もあります。ptrace やレジスタ取得に関するエラーが出たら、表示を残して原因を確認します。コマンドの成功と停止位置を確認できるまでは、後続の観察を進めないでください。

この場合、プログラムの計算が間違っているとは限りません。権限の変更や別の実行環境が必要かは、エラー内容を確認してから判断します。この追加実験ができなくても、前の４つの実験は進められます。

この追加実験の区切りは、保存されていた戻りアドレスと、ret 直後の命令の位置が一致することを確認できたときです。具体的なアドレスの数字を暗記する必要はありません。

ここでの区切りは、命令の変更が結果に与える影響を説明でき、アセンブリの命令が機械語のバイト列へ変換されたことを確認できたときです。機械語の符号化を暗記する必要はありません。

４理解チェック

まず自分で答えを考え、その理由まで言葉にしてから解説を開いてください。

問い１：まだ実行していない命令列を読む

同じ環境で、次の計算部分を持つ main を動かすと、終了状態は何になりますか。２つのレジスタの変化を説明してください。

mov rax, 9
mov rcx, rax
sub rax, 4
add rcx, 2
mov rax, rcx
ret
解説を読む

１１です。コピー直後は両方９、減算後は rax が５、加算後は rcx が１１です。最後に１１を rax に入れます。減算で作った５はそこで上書きされます。コピー先が独立していることと、返す場所の取り決めを使って説明できます。

問い２：ソースを変えたのに結果が変わらない

命令を変更して保存した後、前と同じ結果が表示されました。「理解している命令の意味が間違っている」と決める前に、何を確認しますか。

解説を読む

再ビルドしたか、そのビルドは成功したか、作ったファイルと実行したファイルが同じか、直後に終了状態を確認したかを調べます。そのうえで、変更した値が後の命令で上書きされていないかを追います。観察結果には、命令の意味だけでなく、どのファイルを実行したかも関わります。

問い３：終了状態から、どこまでわかるか

終了状態が９だったことだけから、「途中で必ず７と１２を経由した」と言えるでしょうか。

解説を読む

言えません。最初から９を入れて返す命令列でも同じ結果になります。途中状態についての説明は、実行した命令列とその意味に基づいています。途中の値を直接確認したいなら、その時点で停止してレジスタを調べるなど、追加の観察が必要です。

問い４：最初の問いに戻る

「コンパイラが出力するコードは、どう実行され、計算結果を生むのか」を、アセンブラ、機械語、レジスタ、呼び出し元という言葉を使って説明してください。

説明の骨組みを読む

今回の方式では、コンパイラが出力したアセンブリをアセンブラが機械語へ変換し、リンクを経て実行ファイルになります。実行時、ＣＰＵは機械語の命令に従ってレジスタなどの状態を変えます。関数は計算結果を決められた場所へ置いて呼び出し元へ戻ります。この章では、その結果を終了状態を通して観察しました。

説明に詰まったら、対応する理論や実験へ戻ります。そこで得た説明や区別を、この章の理論本文にも反映して育てていきます。
