ライブラリの本体は、どこにある？

スタティックリンクと
ダイナミックリンク

本体を実行ファイルに取り込むか、別のファイルから読み込むか。
ファイルの違いを、メモリ上の関数呼び出しまでつなぐ。

この章の到達点同じ関数呼び出しが、静的リンクと動的リンクでどこにある機械語へ進むのか、説明できる。

原書「スタティックリンクとダイナミックリンク」に対応。Linux・x86-64・ELFを想定。原書で説明が短い動的リンク部分は、ELF仕様などをもとに補足した。図と例は本教材独自のもの。

01関数の本体を、いつ結び付ける？

第３章ではオブジェクトファイルを結び、第７章では実行ファイルをメモリに配置した。今回は、他の人が用意した関数の本体を、いつ自分のプログラムへ結び付けるかを考える。

呼ぶ側：main.c
int value(void);       // 関数があることと、その型を宣言

int main(void) {
    return value();    // 本体は別のファイルにある
}
ライブラリにする側：value.c
int value(void) {
    return 13;
}

main.cだけをコンパイルした main.o には、mainの機械語と「valueを呼びたい」という参照がある。valueの本体はまだ入っていない。第３章のシンボルは、このような関数や変数を識別する名前だった。

valueを使えるようにする道は２つある。スタティックリンク（静的リンク）では、必要な本体を実行ファイルに取り込む。ダイナミックリンク（動的リンク）では、実行時にも別の共有ライブラリを使い、本体のあるアドレスへつなぐ。

02静的リンク：本体を取り込む

静的ライブラリの .a は、複数の .o をまとめたアーカイブ。圧縮されたソースコード集ではなく、コンパイル済みの部品を入れる容器だ。

リンカはmain.oに足りないvalueの定義を探し、ライブラリ内の必要なオブジェクトを取り込む。その部品が別の関数を必要とすれば、さらに定義を探す。

Linux・GCCで、このライブラリを静的に結ぶ
cc -c main.c -o main.o
cc -c value.c -o value.o
ar rcs libvalue.a value.o
cc main.o ./libvalue.a -o app-a

./app-a
echo $?     # 終了ステータスは13

ar rcs はアーカイブを作り、シンボル索引も用意する。ar t libvalue.a なら中のファイル名を見られる。この例はmain.oの後ろにライブラリを置き、先に現れた未解決の参照を解決する。

このコマンドが静的に結ぶのはlibvalue.aの部分。標準ライブラリなどは動的リンクのままの場合がある。全体を静的リンクするなら cc -static main.o ./libvalue.a -o app-static と明示する。対応する静的ライブラリが開発環境に必要。

取り込んだvalueの実装を更新するには、新しい部品で実行ファイルを再リンクする。元の.aだけを差し替えても、できあがった実行ファイルの中身は変わらない。

参照：GNU ldのアーカイブ検索・GCCのリンクオプション。

03動的リンク：実行時にも結び付ける

共有ライブラリ .so は、実行時に読み込める形にリンクされたファイル。中には関数の機械語やデータがある。別のファイルであっても、別のプログラムを起動して会話するわけではない。呼ぶ側と同じプロセスの仮想メモリに配置する。

起動時にも「つなぐ」処理がある

ファイルを作るリンカは、必要な共有ライブラリや、起動後に調整する参照の情報を出力する。Linuxの通常の動的実行ファイルでは、OSが起動した動的リンカ（ld.soなど）が共有ライブラリを探して読み込み、シンボルと実際のアドレスを対応付ける。ここでも第３章の「シンボル解決」と「再配置」が登場する。

同じvalue.cを、共有ライブラリにする
cc -fPIC -c value.c -o value.pic.o
cc -shared value.pic.o -o libvalue.so
cc main.o -L. -lvalue -Wl,-rpath,'$ORIGIN' -o app-so

./app-so
echo $?     # こちらも終了ステータスは13

-shared は共有ライブラリを作る指定。-L. はリンク時に現在のディレクトリを探す指定で、-lvalue はlibvalueを使う指定。同じ場所に.aと.soの両方があれば、この通常の動的リンクでは.soが選ばれる。

-Wl, は後続の指定をリンカへ渡す。ここでは -rpath で実行時の探索先を記録し、$ORIGIN は実行ファイルのあるディレクトリに展開される。シェルに先に展開させないため、一重引用符で囲んでいる。-L. だけでは実行時の探索先の指定にならない。

上のコマンドはLinuxのELF・GCCを想定。macOSでは形式・拡張子・探索方法が異なる。まずは「作るときの探索」と「実行するときの探索」を分けて読む。

参照：Linuxの動的リンカとライブラリ探索・ELFの動的リンク。

04アドレスが変わっても呼べる仕組み

共有ライブラリの配置先は、実行するたびに同じとは限らない。それでもvalueを呼べるように、呼ぶ側が使う名前と、実際の呼び先アドレスを結ぶ仕組みを用意する。

x86-64のELFでよく使われる方法が、PLTという短い中継コードと、GOTというアドレスを入れる表だ。先に役割だけ見ると、「中継コードから表を読み、表に入った住所へ進む」仕組みになる。

呼び出しの形の例（Intel記法、周囲の命令を省略）
call value@PLT     # 中継コードへ。戻り先はスタックに保存
# 呼び出し後の処理が続く

この表の値を起動時に埋める方式を即時束縛と呼ぶ。設定によっては、最初の関数呼び出しで本体の住所を解決する遅延束縛も使う。後者でも、通常の依存ライブラリそのものは起動時に読み込まれる。「呼ぶたびにライブラリ全体を探し直す」わけではない。

第１章と同じく、命令を追うのはRIP、スタックの先頭を指すのはRSP。共有ライブラリの関数へ進んでも、戻り先のアドレスは同じスレッドのスタックに積まれ、返り値13はEAXに入る。

「共有」は、変数の値まで他のプログラムと共通という意味？

同じ.soを使うプロセスどうしで、読み取り専用のコードの物理ページを共有できる。各プロセスは独立した仮想アドレス空間を持ち、ライブラリの書き換え可能な通常のグローバル変数は、原則としてプロセスごとに別の状態になる。

参照：AMD64 ABIのPLT・GOT・即時・遅延束縛。

05PIEとの違いと、使い分け

原書には「PIEを作る際に、その再配置は使えない」というリンクエラーが出てくる。ここで話を分けよう。静的／動的はライブラリをどう結ぶか。PIEかどうかは実行ファイルを配置先に依存しにくく作るか。別の選択だ。

用語・指定決めること
-static共有ライブラリに対する動的リンクを避け、静的に結ぶ。
-no-piePIEの実行ファイルを作らない。これだけで静的リンクにはならない。
-fPIC主に共有ライブラリ用に、配置先が変わっても使えるコードを生成する。
-fPIE と -pieそれぞれPIE用のコード生成と、PIE実行ファイルのリンクを指定する。

PIEは、実行ファイルをロードするアドレスを変えやすくする形式。ASLR（配置先をランダム化する仕組み）と組み合わせて使われる。-fPIC を付ければ、すでに書かれた任意のアセンブリが自動的に修正されるわけではない。自作コンパイラが出す命令や再配置も、その形式に適合させる必要がある。

原書のエラーは、PIEで許されない再配置を使っていることが直接の問題。動的リンクそのものを否定するエラーではない。非PIEが目的なら -no-pie、PIEが目的なら生成コードを対応させる、と目的から考える。

どちらを使うと、何が変わる？

観点静的に取り込む共有ライブラリを使う
配布取り込んだ.aは実行時に不要。互換性のある.soと探索先が必要。
更新修正を反映するには通常再リンク。互換性を保つ更新なら、本体の再リンクなしで次の起動から使える場合がある。
サイズ・共有各実行ファイルに部品を含む。ファイルや読み取り専用のコードページを共有できる。
起動・呼び出し実行時の外部参照の解決を減らせる。読み込み・再配置や呼び出しの中継が加わり得る。

静的でもOS・CPUとの互換性やデータファイルなどの依存は残る。動的でも、どんなバージョンの.soへ自由に交換してよいわけではない。ABIが合うことが必要で、起動済みのプロセスが自動的に新しいコードへ切り替わるとも限らない。

参照：GCC：-static・-no-pie・-static-pie・-fPIC・-fPIE。

07理解を確かめる

ヘッダに宣言があれば、関数の本体も手に入る？

宣言は型などを伝えるもの。本体は別に必要で、静的なら取り込み、動的なら共有ライブラリの定義へ実行時につなぐ。

.aをリンクしたら、実行時にもその.aを読む？

取り込んだ部品は実行ファイルの中にある。その.aは実行時には不要。

共有ライブラリの関数は、別プロセスで動く？

通常の関数呼び出しでは、呼び出し元と同じプロセス内のコードを同じスレッドが実行する。

動的リンクは、呼ぶたびに名前を検索する？

常にそうではない。起動時や最初の呼び出しで解決し、そのアドレスを利用する方式がある。

共有ライブラリから戻るときも、スタックを使う？

使う。callが保存した戻り先をretで読み、呼び出し元へ戻る。返り値と戻り先の住所は別のもの。

-no-pieを付ければ、完全な静的リンクになる？

ならない。配置形式とライブラリの結び方は別。静的リンクは-staticなどで指定する。

ライブラリを更新すれば、既存の実行ファイルの動作も変わる？

静的に取り込んだ部分は通常再リンクが必要。動的に使う部分は、ABIや探索条件が合えば次回起動時などに更新版を使える。

実際のファイルでは、何を見ればよい？

Linuxで、作成した２つのファイルを観察する
ar t libvalue.a
readelf -d app-a
readelf -d app-so
readelf -l app-so

readelf -d は動的リンク用の情報を表示する。app-soの NEEDED にはlibvalue.soへの依存が現れ、app-aにはその依存がないはず。ただしapp-aにもlibc.soなどへの依存が残る場合がある。readelf -l の INTERP は、起動に使う動的リンカの情報を確認する場所。
