別々に作った命令を、ひとつにつなぐ

分割コンパイルと
リンク

別のファイルにある関数を、その中身を読まずに呼び出せる。
「呼び方を知る」と「呼び出し先を決める」を分けると、その仕組みが見えてくる。

この章の到達点ヘッダだけでは実行できない理由と、変更したファイルだけを作り直せる理由を説明できる。

原書の「電卓レベルの言語の作成」に続く章。対象は分割コンパイルの概念とステップ８。図とコードは本教材独自の例。コマンドはLinux・GCC／GNUツールを想定する。

01ファイルを分けても呼び出せる

第１章の「13を返す関数を呼び、１を足す」を、２つのCファイルに分ける。この章では、コンパイラ自身を作るCコードの整理を学ぶ。自作言語に新しい計算機能を足す段階ではない。

value.h：共通の宣言
#ifndef VALUE_H
#define VALUE_H
int value(void);
#endif
main.c：呼び出す側
#include "value.h"

int main(void) {
    return value() + 1;
}
value.c：実体を用意する側
#include "value.h"

int value(void) {
    return 13;
}

main.c を処理するコンパイラには、value.c の本体を渡さなくてよい。value() の呼び方はヘッダで確認し、呼び出し先が未確定のままオブジェクトを作れる。

同じフォルダに３ファイルを置いた場合
cc -std=c11 -Wall -Wextra -c main.c -o main.o
cc -std=c11 -Wall -Wextra -c value.c -o value.o
cc main.o value.o -o demo
./demo
echo $?    # 14

-c はリンクの手前、オブジェクト生成まで進める指定。最後の cc はコンパイラのドライバとしてリンカなどを起動する。cc main.c value.c -o demo と一度に頼む書き方でも、通常は別々の翻訳単位として処理される。ここではLTOなどの全体最適化は扱わない。

分割すると役割を整理できるうえ、変更していない部分の .o を再利用できる。ただし、変更後には必要な .o を作り直し、通常は実行ファイルも再リンクする。

参照：GCCの処理段階と -c。

02ヘッダが渡すのは型の情報

int value(void); という宣言から、コンパイラは「引数なしで呼び、intの結果を受け取る」とわかる。どの命令で13を計算するか、実行時に何番地に置くかは、この宣言には含まれない。

ヘッダには、共有する関数宣言、構造体の型定義、typedef などをまとめる。本体を書く value.c にも同じヘッダを入れると、宣言と実装の型の食い違いをその翻訳単位で検出できる。

#ifndef〜#endif は何を防ぐ？

同じ翻訳単位の中でヘッダを重ねて取り込むことを防ぐ「インクルードガード」。別々の .c に１回ずつ取り込むことは防がない。したがって、ヘッダに外部公開する関数本体を書いたときの重複定義対策にはならない。

定義も宣言の一種。「ヘッダには定義を一切書けない」という意味ではない。構造体の型定義や、用途を限定したstatic inline関数などは書ける。この章では、外部から使う通常の関数本体・変数の実体を１つの .c に置く。

参照：GCCのヘッダの説明、インクルードガード。

03名前から呼び出し先を決める

シンボルは、関数や変数を名前で参照するための情報。今回の main.o は「valueを使う」、value.o は「valueの実体はここ」と記録する。リンカは参照と定義を対応付け、部品の配置を決め、必要な修正をする。

callには、８バイトの住所をそのまま埋める？

x86-64の直接呼び出しの一例では、call は「次の命令から呼び出し先までの差」を32ビットで持つ。下はリンク後の配置を仮定した説明用の数値だ。

ここで書き換えるのは出力するファイル内の参照箇所。リンカがプログラムを実行して、スタックに戻り先を積むわけではない。第１章の call・ret は、できた実行ファイルを動かすときの仕事だ。

部品に残る名前を確認する
nm main.o
nm value.o
objdump -dr -M intel main.o

nm の通常の表示で U value は未定義の参照、T value はコード領域にある外部公開の定義を示す。objdump -dr は命令と再配置情報を一緒に見る。具体的なアドレス・命令列・記号は環境や最適化で変わる。

04宣言・定義とリンクエラー

共有するヘッダ：存在と型を伝える
extern int total;
int value(void);
１つのCファイル：実体を用意する
int total = 0;

int value(void) {
    return 13;
}

extern int total; だけでは保存場所を作らない。ファイルスコープの int total; は仮定義で、その翻訳単位内に別の定義がなければゼロ初期化される定義として扱われる。共有ヘッダには extern の宣言、実体は１か所、と区別すると迷いにくい。

状態止まる場所・理由
valueの宣言が見えないコンパイル時に呼び方を確認できない。現代のCでは宣言なしの関数呼び出しは診断対象。
宣言はあるが、value.oをリンクに渡さないリンク時に参照先を見つけられない。典型的には undefined reference。
通常の外部定義を２つ渡すリンク時に定義が重複。典型的には multiple definition。
ヘッダに関数本体を書き、２つの.cで取り込む同じ外部定義が２つの.oに生まれる。ガードがあっても、翻訳単位が別なので防げない。

リンク成功は、型も実行結果も正しいという保証ではない。通常のリンカはCの関数宣言の型を完全には照合しない。共通ヘッダで呼び出し側と定義側の型をそろえることが大切だ。

static は「スタックに置く」という意味？

違う。ファイルスコープの関数や変数に付けるstaticは、名前をその翻訳単位の内側に限定する。関数内のstatic変数は、関数から戻った後も値を保持する。どちらも「スタックに積む」という指定ではない。コンパイラの非公開の補助関数には、ファイルスコープのstaticが役立つ。

05ライブラリもコンパイル済みの部品

#include <stdio.h> で読み込むのは、printfなどを使うための宣言。printfの実装はC標準ライブラリ側にある。通常の cc によるリンクでは標準ライブラリが追加されるため、ソースが１ファイルでも外部の部品を使っている。

アーカイブ（.a）は、複数の .o をまとめる入れ物。リンカは、必要な未解決シンボルを満たすメンバーを取り込める。通常は関数１個単位ではなく、まずオブジェクト単位で選ぶ。

上のvalue.oをアーカイブにまとめる
ar rcs libvalue.a value.o
cc main.o -L. -lvalue -o demo
./demo
echo $?    # 14

-L. は現在のフォルダもライブラリ検索に使う指定、-lvalue はlibvalueというライブラリを探す指定。このフォルダにlibvalue.aだけがある前提だ。GNUリンカではアーカイブを置く順番が重要なので、必要とする main.o を前に置く。

ここではvalueの実装を実行ファイルへ取り込むが、標準ライブラリまで静的リンクする指定ではない。原書の「C標準ライブラリとアーカイブファイル」は見出しのみなので、この節は補足として加えている。

参照：GNU ar、GNU ldのライブラリ検索。

06ステップ８と作り直す範囲

原書のステップ８では、コンパイラを main.c・parse.c・codegen.c に分け、共有する宣言や型を 9cc.h に集める。処理の意味を変えずに置き場所を変える段階なので、分割の前後で既存のテスト結果が一致することを確かめる。

ファイル担当
main.c入力から解析・コード生成へ処理をつなぐ。
parse.cトークンや構文解析を扱う。
codegen.c構文木からアセンブリを出す。
9cc.hファイル間で共有する型・関数宣言・extern宣言。

Makefileは「何が何に依存するか」を書く

まず小さなvalueの例で読む。ターゲット: 依存ファイル の下に、そのターゲットを作るコマンドを書く。ターゲットがないか、依存ファイルより古ければ作り直す。

valueの例のMakefile（コマンド行の先頭はタブ）
CC = cc
CFLAGS = -std=c11 -Wall -Wextra -g
OBJS = main.o value.o

demo: $(OBJS)
	$(CC) $(LDFLAGS) -o $@ $(OBJS) $(LDLIBS)

$(OBJS): value.h

%.o: %.c
	$(CC) $(CPPFLAGS) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
	rm -f demo $(OBJS) libvalue.a

$@ は作るターゲット名、$< は最初の依存ファイル名。%.o: %.c は対応する.cから.oを作るパターンルール。.PHONY はcleanをファイル名として扱わないための指定だ。

変更するファイルを選ぶ

一度ビルドが成功し、全ファイルが最新の状態を基準にした観察モデル。選ぶたびに、その基準から変更した場合を表示する。

変更がないので、コンパイルもリンクも不要。

実行するコマンドなし

makeは通常、内容の意味ではなく更新時刻と依存関係で判断する。ヘッダへの依存を書き忘れると、型を変えても古い.oを再利用してしまう。コンパイルオプションだけの変更も、このMakefileでは自動検出しないので作り直しが必要になる。

原書のMakefileを読むときの補足

$(wildcard *.c) は.cの一覧、$(SRCS:.c=.o) は拡張子を.oに置き換えた一覧を作る。原書では組み込みのコンパイル規則を利用しているが、上の例ではコマンドを明示した。静的リンクを指定する -static はリンク段階に渡す必要があるため、必要なら LDFLAGS = -static とする。CFLAGSに書くだけでリンク用のコマンドに必ず渡るわけではない。

07理解を確かめる

ヘッダを入れればvalueの実体も使える？

呼び方はわかるが、実体は増えない。定義を含むvalue.o、または対応するライブラリをリンクする必要がある。

main.oに未解決のvalueがあるのは失敗？

分割コンパイルでは正常な途中状態。最終的なリンクで参照先を用意できればよい。

value.cのreturn 13をreturn 20に変えたら？

ヘッダを変えなければvalue.oを作り直して再リンクする。main.oは再利用でき、実行結果は21になる。

リンカがcallの戻り先をスタックに積む？

積まない。リンカはファイル内の呼び出し先への参照を整える。実行時にCPUがcallを実行すると、その時の次の命令位置をスタックに積む。

ヘッダを変更したら、どこまで作り直す？

そのヘッダに依存する翻訳単位から.oを作り直し、再リンクする。この例では両方の.cがvalue.hを使うので、両方が対象。

第２章までの「文字列 → AST → 命令」は１つのコンパイラの中の処理。この章の「.c → .o → 実行ファイル」は、そのコンパイラ自体を組み立てる処理。２つの流れを区別して原書へ戻ろう。
